## 1. Ringkasan eksekutif

Tingkat risiko keseluruhan: **Tinggi**, turun ke **Sedang** setelah SEC-42 diperbaiki (perbaikannya kecil dan lokal di agent).

Rencana 3 mengerjakan tiga hal yang dijadwalkan audit Rencana 2: peran yang dipin (SEC-28 butir 1), sumber yang dipin (SEC-28 butir 3), dan catatan audit (SEC-17). Pekerjaan dasarnya rapi. Tabel penolakan §5.5 diterapkan persis, termasuk `mysql.startUntil` dan `mysql.dropUser` yang ditambahkan saat review. Berkas pin diperiksa kepemilikan, mode, dan isinya, dan bila tidak bisa dipercaya agent menolak semua perintah yang dijaga (gagal tertutup). Penulisan pin atomik. Klaim pertama tidak pernah menimpa pin lain. CLI lokal adalah satu-satunya jalan mengubah peran `master`.

Di panel, semua 13 route POST baru dan yang diubah lolos CSRF (52/52 kombinasi Origin asing, `null`, tanpa Origin, dan `Sec-Fetch-Site: cross-site` dijawab **403**). Semua route GET baru ada di balik login dan membawa baseline header lengkap. String dari agent yang jahat (versi, UUID, GTID, error MySQL, host sumber, filter) ter-escape di 9 halaman dan fragmen yang diuji. Token bot Telegram tersegel AES-256-GCM, tidak pernah muncul di log, DB, HTML, audit, atau SSE (dicek setelah kirim tes yang gagal), dan bentuknya divalidasi sehingga tidak bisa menyisip path. Pesan Telegram dibangun dari teks milik panel, bukan teks error MySQL. Alamat Bot API tidak bisa diatur dari UI.

Satu temuan **Tinggi** membatalkan tujuan utama pin master:

1. **SEC-42**: `mysql.createDumpUser` (dan `mysql.createReplUser`) tidak ada di tabel penolakan master. Panel yang dibobol bisa (a) membuat akun `dbpanel_<apa saja>@'%'` dengan `RELOAD, LOCK TABLES, SELECT ON *.*`, lalu menjalankan `RESET MASTER` (semua binlog dan riwayat GTID master hilang) dan menahan `FLUSH TABLES WITH READ LOCK` (semua penulisan SIMRS berhenti); (b) mengambil alih `dbpanel_repl`: sandinya diganti dan haknya ditukar, sehingga semua replika putus (1045) begitu menyambung ulang. PoC di mysqld 8.0.46 dengan agent yang dipin `master`: `dropDatabases` dan `dropUser dbpanel_repl` ditolak, tetapi `createDumpUser` lolos, `RESET MASTER` berhasil (`gtid_executed` `…:1-6` → `""`), dan INSERT root tertahan `ERROR 1205`. Ini mengembalikan dampak SEC-27 yang sudah diperbaiki di Rencana 2.

Dua temuan **Sedang**:

- **SEC-43**: pin sumber dan peran replika bisa dilepas oleh panel sendiri (`stopReplica` → `resetReplica` → `releaseRole`), lalu replika diarahkan ke host mana pun. PoC: pin `127.0.0.1:<port>` hilang dan diganti `10.66.66.66:<port>` tanpa menyentuh host. README menyatakan sumber "hanya diubah di server itu sendiri".
- **SEC-44**: `audit_log` menyimpan input mentah yang ditolak tanpa batas ukuran (`detail_json`), dan barisnya tidak bisa dihapus. PoC: 200 permintaan login dalam ±1 detik menambah ±12 MB ke `panel.db` yang tidak bisa dipangkas lewat produk. Host panel juga host replika MySQL.

Lima temuan Rendah (ketahanan ubah dan kelengkapan audit log, banjir peringatan dari agent yang dibobol, kepercayaan kanal Telegram, bootstrap dan visibilitas pin, kesalahan admin pada Resync dan Jangan ganggu), dua Info, dan dua risiko Diterima.

## 3. Model ancaman delta

Model ancaman Rencana 1 (§3) dan Rencana 2 (§3, butir 8–11) tetap berlaku. Rencana 3 menambah aset, batas, dan penyerang berikut:

- **Aset baru:** berkas pin `/etc/dbpanel/role` dan `/etc/dbpanel/source` (batas kepercayaan baru antara panel dan agent); token bot Telegram (tersegel di `panel.db` dengan `panel.key`); kanal Telegram operator (dipercaya operator untuk bertindak pada malam hari); `audit_log` (bukti forensik); data kesehatan per server (`server_health.snapshot_json`, `status_events`, `alerts`).
- **Batas yang berubah:** sebelum Rencana 3, panel yang dibobol setara dengan root MySQL di semua server (SEC-28). Sesudahnya, agent master yang dipin **seharusnya** menolak semua perintah yang merusak data, binlog, atau ketersediaan master. Audit ini menguji batas itu.

12. **Panel yang dibobol vs master/replika yang dipin** (butir 11 Rencana 2, kini dengan pin): mencari perintah di luar tabel §5.5 yang tetap merusak, rantai `releaseRole`, perintah yang menulis pin (`configure`, `configureReplication`, `dumpFrom`/`cloneFrom`, `Bootstrap` via `role_hint`), dan berkas pin itu sendiri (symlink, izin). Catatan: panel tidak bisa menulis berkas di host agent; satu-satunya jalur ke berkas pin adalah perintah agent.
13. **Penyerang on-path di LAN UI** (SEC-23 diterima): kini UI juga membawa token bot Telegram dan tombol destruktif baru. Route POST baru dan endpoint GET fragmen/hitungan/log diuji untuk CSRF dan kebocoran lintas asal.
14. **Admin berkemampuan rendah** yang salah klik: konfirmasi ketik-nama, bawaan yang destruktif, Jangan ganggu.
15. **Agent jahat atau server DB yang dibobol** (sertifikat sah): laporan kesehatan palsu atau beracun (batas 64 KiB, watermark Seq, string HTML, GTID panjang), banjir peringatan ke Telegram, injeksi teks ke pesan Telegram.
16. **Sisi Telegram:** kebocoran token (log, error, audit, SSE, HTML), SSRF lewat alamat yang bisa diatur, tautan di pesan, data yang keluar dari rumah sakit ke layanan pihak ketiga.
17. **Campuran versi agent:** panel baru dengan agent lama (tanpa pin), agent baru dengan pin di server yang dikonfigurasi sebelum pin ada (bootstrap), downgrade.

### SEC-42 — Pin master dilewati lewat `mysql.createDumpUser`/`createReplUser`
- **Tingkat:** Tinggi. CVSS-ish `AV:N/AC:L/PR:H/UI:N/S:C/C:L/I:H/A:H` ≈ 8.7. Prasyaratnya panel dibobol, yaitu persis penyerang yang menjadi alasan pin dibuat (spesifikasi §5.5, komentar `pins.go:20-25`: "a compromised panel can therefore never turn a production master into a replica, drop or replace its data…").
- **Dieksploitasi oleh:** pemegang kendali panel (proses web root, SEC-06 ditunda ke Rencana 4; sesi lewat HTTP polos, SEC-23) atau pencuri kunci CA panel.
- **Lokasi:**
  - `internal/agent/drivers/mysql/pins.go:56-72` (`roleRefuses[master]` tanpa `mysql.createDumpUser`, `mysql.createReplUser`, `mysql.restart`, `mysql.connect`), `pins.go:502-529` (`refusedByRole`: aturan berparameter hanya untuk `configure`, `setReadOnly`, `dropUser`);
  - `users.go:62-83` (`mysql.createDumpUser` **tanpa** `d.allow(...)` sama sekali; host bebas termasuk `%`; nama cukup berawalan `dbpanel_`);
  - `users.go:40-60` (`mysql.createReplUser`: `allow` hanya menolak di peran `replica`);
  - `users.go:190-239` (`createAccount`: akun yang sudah ada di-`ALTER USER … IDENTIFIED BY`, lalu `REVOKE ALL` dan `GRANT <grants>`);
  - `users.go:36` (`dumpGrants = "SELECT, RELOAD, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT"`);
  - `configure.go:72-85` (`mysql.restart` tanpa `allow`).
- **Serangan dan dampak** (setiap baris adalah satu pesan ke agent master yang **dipin `master`**; tidak satu pun ditolak):

  | Perintah dari panel jahat | Efek di master produksi |
  |---|---|
  | `mysql.createDumpUser{User:"dbpanel_x", FromHost:"%", Password:P}` lalu login dari mana pun di LAN (`bind_address=0.0.0.0`, SEC-40) dan `RESET MASTER` | semua binlog dan riwayat GTID hilang; semua replika error 1236 saat menyambung ulang; rantai PITR putus (di 8.4+ `RESET BINARY LOGS AND GTIDS`, juga cukup `RELOAD`) |
  | sama, lalu `FLUSH TABLES WITH READ LOCK` dan sesi dibiarkan hidup | semua penulisan SIMRS berhenti sampai sesi dibunuh |
  | sama, lalu `LOCK TABLES simrs.pasien WRITE` | tabel itu tidak bisa dibaca atau ditulis aplikasi |
  | `mysql.createDumpUser{User:"dbpanel_repl", FromHost:"%", Password:P}` | akun replikasi bersama diganti sandinya, `REPLICATION SLAVE` dicabut dan diganti hak dump; semua replika putus (1045) saat menyambung ulang; penyerang memegang akun ber-RELOAD bernama resmi |
  | `mysql.createReplUser{User:"dbpanel_repl", …, Password:P}` | sandi akun replikasi diganti: semua replika putus (ketersediaan); penyerang mendapat `BACKUP_ADMIN` (CLONE seluruh master) |
  | `mysql.restart` berulang | master restart terus (SIMRS berhenti); spesifikasi "master tidak pernah direstart tanpa klik manusia" hanya ditegakkan panel |

  Pin hanya menolak "perintah yang namanya berbahaya". Perintah pembuatan akun tidak dianggap berbahaya, padahal hak yang diberikannya cukup untuk merusak binlog dan ketersediaan. Perbaikan SEC-27 Rencana 2 (memindahkan RELOAD dari akun replikasi bersama ke akun dump sementara) jadi tidak berarti terhadap panel yang dibobol: panel bisa membuat akun dump kapan saja, dengan host apa saja, dan tanpa batas umur, sedangkan penyapuan `sweepDumpUsers` juga dipicu oleh panel.
- **Bukti (agent nyata, `Pins` dengan `role=master`, master dengan replika yang mengikutinya, mysqld 8.0.46):**
  ```
  role pin = "master"
  dropDatabases on pinned master: ok=false err=server ini dipin sebagai master; perintah mysql.dropDatabases ditolak. …
  dropUser dbpanel_repl on pinned master: ok=false err=server ini dipin sebagai master; perintah mysql.dropUser ditolak. …
  BEFORE gtid_executed="17624624-d6c4-11f1-a65f-02fc00000001:1-6"
  createDumpUser{dbpanel_repl@%} on pinned master: ok=true err=<nil>
  grants dbpanel_repl now: [GRANT SELECT, RELOAD, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER ON *.* TO `dbpanel_repl`@`%`]
  createDumpUser{dbpanel_x@%} on pinned master: ok=true err=<nil>
  dbpanel_x reads simrs.pasien: "Budi"
  RESET MASTER as dbpanel_x OK; AFTER gtid_executed=""
  root INSERT while dbpanel_x holds FTWRL: err=Error 1205 (HY000): Lock wait timeout exceeded; … after 2s
  replica after (STOP/START REPLICA): IO=Connecting SQL=Yes Last_IO_Errno=1045 Error connecting to source 'dbpanel_repl@127.0.0.1:…'
  ```
- **Perbaikan minimal** (semuanya di agent, berlaku saat peran `master` dipin):
  1. Masukkan `mysql.createDumpUser`, `mysql.createReplUser`, dan `mysql.restart` ke `refusedByRole` sebagai aturan berparameter:
     - `createDumpUser`: nama harus cocok `^dbpanel_dump_[0-9a-f]{8}$`; host harus literal IP (`net.ParseIP`, tanpa `%`/`_`); **tolak bila akun sudah ada** (agent tidak pernah meng-`ALTER` akun yang ada).
     - `createReplUser`: hanya `dbpanel_repl`; bila akun sudah ada, terima hanya bila sandinya sama (cek dengan `mysql_native`/`caching_sha2` tidak praktis, jadi lebih sederhana: tolak `ALTER` pada master yang dipin; rotasi sandi lewat CLI lokal).
     - `restart`: tolak pada master yang dipin kecuali `configure` terakhir di proses ini melaporkan `NeedsRestart` (satu restart per konfigurasi), atau minta token konfirmasi Rencana 4.
  2. Umur akun dump ditegakkan agent master sendiri: loop monitor agent menghapus `dbpanel_dump_%` yang lebih tua dari, misalnya, 6 jam, tanpa menunggu panel. Pertimbangkan `PASSWORD EXPIRE INTERVAL 1 DAY` dan `FAILED_LOGIN_ATTEMPTS`.
  3. Test regresi: pada master yang dipin, `createDumpUser{dbpanel_repl}`, `createDumpUser{…@'%'}`, `createDumpUser` untuk akun yang sudah ada, dan `createReplUser` untuk akun yang sudah ada harus ditolak.
  4. (Rencana 4) Dump tanpa akun jaringan ber-RELOAD: agent master yang menjalankan `mysqldump` dengan akun lokal dan mengalirkannya lewat kanal agent, sehingga tidak ada akun RELOAD yang bisa dibuat atas permintaan panel.
- **Kapan:** sebelum rilis (butir 1–3, murah dan lokal); butir 4 di Rencana 4.

### SEC-43 — Pin sumber dan peran replika bisa dilepas panel sendiri, lalu replika diarahkan ke host mana pun
- **Tingkat:** Sedang. CVSS-ish `AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:L` ≈ 6.0. Targetnya replika, bukan master. Namun replika dipakai untuk laporan dan sebagai cadangan, dan Rencana 4 akan mempromosikan replika menjadi master.
- **Dieksploitasi oleh:** panel yang dibobol.
- **Lokasi:** `internal/agent/drivers/mysql/replication.go:150-163` (`mysql.resetReplica` diizinkan pada peran `replica`), `replication.go:165-188` (`mysql.releaseRole`: syaratnya hanya "tidak ada konfigurasi replikasi" dan `binlog_dump_threads=0`), `pins.go:330-341` + `pins.go:534-542` (`Release` menghapus **kedua** berkas, peran dan sumber), `pins.go:69-71` (peran `replica` hanya menolak `createReplUser`; `dropDatabases`, `dumpFrom`/`cloneFrom` ke sumber yang dipin, dan `resetReplica` diizinkan), README baris 308-311 ("peran `master` dan sumber hanya diubah di server itu sendiri").
- **Serangan dan dampak:** tiga perintah yang semuanya diizinkan di replika yang dipin (`stopReplica`, `resetReplica`, `releaseRole`) mengubahnya menjadi server `unassigned` tanpa pin. Setelah itu panel bebas menjalankan:
  - `configureReplication` + `startReplica` ke master palsu: replika menerapkan event binlog penyerang;
  - `dumpFrom{DropExisting}` dari host penyerang: semua database replika diganti, dan aliran dump dijalankan klien `mysql` dengan akun admin replika (`ALL PRIVILEGES`; `--binary-mode` menutup `\!` (SEC-26), tetapi SQL apa pun tetap berjalan sebagai admin);
  - `cloneFrom` donor penyerang: seluruh instance diganti, termasuk `mysql.user`;
  - klaim pertama berikutnya memasang sumber baru, yang kini milik penyerang.
  Tujuan SEC-28 butir 3 ("perubahan sumber membutuhkan konfirmasi lokal") tidak tercapai. Pin sumber hanya menghalangi panel yang lupa melepasnya. Spesifikasi §5.5 memang mengizinkan `releaseRole` dari panel demi kenyamanan ("server bisa dipakai lagi dari panel tanpa terminal"). Ledger mencatat "replica release→reconfigure chain is by design". Namun README menjanjikan hal sebaliknya kepada operator.
- **Bukti (replika yang mengikuti master nyata, pin `replica` + `127.0.0.1:<port>`):**
  ```
  configureReplication to attacker before chain: ok=false err=server ini dipin mengikuti sumber 127.0.0.1:41435; perintah mysql.configureReplication ke 10.66.66.66:41435 ditolak. …
  mysql.stopReplica: ok=true
  mysql.resetReplica: ok=true
  mysql.releaseRole: ok=true
  pins after chain: role="" source=""
  configureReplication to attacker after chain: ok=true err=<nil>
  pins now: role="" source="10.66.66.66:41435"
  ```
- **Perbaikan minimal:**
  1. `releaseRole` hanya menghapus berkas peran. Berkas sumber dipindah ke `source.released` (atau dibiarkan). `configureReplication`/`dumpFrom`/`cloneFrom` ke sumber lain tetap ditolak sampai root menjalankan `dbpanel agent set-source --clear` atau `set-source <baru>`. Alur "Lepas dan hentikan" dan "Hapus server" tetap berjalan tanpa terminal. Hanya pemakaian ulang server untuk master **lain** yang perlu satu perintah lokal, dan itu sesuai SEC-28 butir 3.

  3. Perbaiki README: sebutkan bahwa panel bisa melepas pin replika, dan apa artinya.

- **Kapan:** README sebelum rilis; butir 1 sebelum Rencana 4 (promote membuat integritas replika setara master).

### SEC-44 — `audit_log` menyimpan input mentah yang ditolak tanpa batas dan tidak bisa dipangkas
- **Tingkat:** Sedang. CVSS-ish `AV:A/AC:L/PR:H/UI:N/S:C/C:N/I:N/A:H` ≈ 5.5. Dampaknya permanen. Host panel juga host replika MySQL (dan agent tertanam), sehingga disk penuh menghentikan replika itu, `panel.db`, dan pemantauan sekaligus.
- **Dieksploitasi oleh:** siapa pun yang memegang sesi admin, termasuk sesi yang dicuri lewat HTTP polos (SEC-23). Juga bug klien atau skrip yang salah.
- **Lokasi:**
  - `internal/panel/web/audit.go:39-50` (`maxAuditOutcome` membatasi `outcome` saja; `detail_json` tidak dibatasi);
  - input mentah yang ditolak masuk `detail`: `handlers_servers.go:219` (`server_create`: `{"name": <input>}`), `handlers_controls.go:147-160` (`replica_resync`: `wipe_list` mentah saat ditolak), `handlers_mysql.go:285-287` (`master_source`: `source_host`/`source_port` mentah), `handlers_auth.go:94` (`login_failed`: username verbatim);
  - `router.go:265-266` (`maxFormBody` 64 KiB per permintaan; tidak ada batas laju untuk POST terautentikasi);
  - `migrations/0004_monitoring.sql:62-70` (trigger `RAISE(ABORT)` pada UPDATE dan DELETE; README: "tidak dipangkas").
- **Serangan dan dampak:** setiap POST yang ditolak validasi menulis sampai ±64 KiB ke tabel append-only. Laju yang terukur di binary sungguhan sekitar 200 permintaan/detik dari satu klien, atau ±12 MB/detik (±1 TB/hari). Baris itu tidak bisa dihapus dari produk. Operator harus memakai `sqlite3`, `DROP TRIGGER`, `DELETE`, dan `VACUUM` sebagai root, yang juga merusak klaim tahan ubah. Banjir yang sama mendorong aksi asli keluar dari tampilan `/audit`, yang hanya menampilkan 500 baris terbaru (SEC-45). Efek samping kecil: `login_failed` mencatat username verbatim, sehingga sandi yang salah diketik di kolom username tersimpan selamanya (ASVS 7.1.1). - **Bukti:**
  ```
  $ curl … --data-urlencode "name@big.txt" /servers     # 60.000 karakter, 400
  audit_log: ('server_create', 'nama server hanya boleh huruf, …', 60013)   <- panjang detail_json
  200 permintaan paralel: elapsed 1.02 s; panel.db 143 KB -> 13,2 MB (+ WAL 4,1 MB)
  ```

- **Perbaikan minimal:**
  1. Batasi `detail_json`, misalnya 2 KiB total. Setiap string dipotong (misalnya 128 rune) dan setiap daftar dibatasi (misalnya 64 elemen).
  2. Untuk input yang **ditolak**, jangan simpan nilainya. Simpan nama field dan panjangnya, atau SHA-256 pendek. Nilai mentah hanya disimpan bila lolos validasi.
  3. `login_failed`: simpan username hanya bila akun itu ada; selain itu `"(tidak dikenal)"` dan hash pendek.
  4. Batas laju per sesi untuk POST yang menulis audit (misalnya 5/detik, burst 20).
  5. Kebijakan retensi yang tetap tahan ubah: arsip bulanan (ekspor bertanda tangan/ber-hash, lalu hapus lewat perintah CLI root yang juga dicatat), bukan "tidak pernah dipangkas".
- **Kapan:** sebelum rilis (butir 1–3 murah); 4–5 nanti.

### SEC-51 — Catatan robustness
- **Tingkat:** Info.
- (a) `mysql.configure{role:"master", server_id:N}` diterima di master yang dipin dan menjalankan `SET PERSIST server_id=N` (`configure.go:156,189-201`). PoC: server_id master diubah menjadi server_id replika. Dengan GTID ON, replika tetap menerapkan transaksi (3/3 baris, GTID sama), jadi tidak ada divergensi senyap di 8.0.46. Tetap sebaiknya: pada master yang dipin, abaikan `ServerID` yang berbeda dari nilai sekarang.
- (b) `Pdeathsig` (`command_linux.go`) dikirim saat **thread OS** pembuat proses anak berakhir, bukan saat proses agent berakhir (perilaku Linux; issue Go #27505). Runtime Go jarang mengakhiri thread kecuali goroutine yang `LockOSThread`, jadi risikonya kecil: anak bisa menerima SIGTERM lebih awal dan job gagal dengan pesan aneh. Pantau di test E2E.
- (c) `monitor/gtid.go`: `last.hi+1` dan `mi.hi-mi.lo+1` bisa overflow pada interval `…:1-18446744073709551615`, sehingga `GTIDGap` negatif (diabaikan karena `> 0`). Pencocokan interval O(n·m) per evaluasi; dibatasi payload 64 KiB dan perlu dua agent jahat sekaligus.
- (d) `hub/conn_ws.go:14`: `readLimit` 4 MiB, sedangkan laporan kesehatan ditolak di atas 64 KiB setelah dibaca seluruhnya. Turunkan `readLimit` (SEC-34 sisa).
- (e) `handlers_jobs.go` `jobLog` memvalidasi `after` sebelum mencari job (400 vs 404). Tidak berdampak.
- (f) Tidak ada semafor untuk perintah sinkron agent (SEC-28 butir 5, ditunda). `monitor.snapshot` dari panel diserialkan `checkMu` dan memakai satu koneksi MySQL, sehingga tidak menambah tekanan `max_connections`.

### 4A. Yang diperiksa dan dinilai aman

- **Tabel penolakan pin** (`pins.go:56-72,502-529`): semua 9 perintah spesifikasi §5.5 untuk master, ditambah `startUntil`, `releaseRole`, dan aturan `dropUser` (hanya `dbpanel_dump_*`); `configure` lintas peran dan `setReadOnly` arah terlarang ditolak di kedua peran; `refuseOnSource` tetap untuk server `unassigned` dan dilewati hanya untuk `setReadOnly{on:false}` pada master yang dipin. Pemeriksaan pin berjalan **setelah** validasi parameter dan **sebelum** MySQL disentuh. Tipe parameter yang tak terduga menghasilkan error (gagal tertutup). Perbandingan sumber `EqualFold` host + port; ejaan host lain ditolak (gagal tertutup, tercatat minor).
- **Berkas pin:** berkas biasa (bukan symlink atau direktori), tidak bisa ditulis grup/lainnya, milik root/euid, ≤ 512 byte, isi dari daftar tetap atau `host:port` yang lolos `sourceHostRe` + `net.ParseIP`. Stat per cek dengan cap ino/uid/mode/mtime/size, sehingga suntingan CLI langsung berlaku. Penulisan via `CreateTemp` di direktori yang sama → `Chmod 0644` → `Sync` → `Rename`. Klaim tidak pernah menimpa pin berbeda (`claimRole`/`claimSource` error). `settled` mencegah `Bootstrap` setelah proses pernah melihat berkas peran. Pin rusak → semua perintah yang dijaga ditolak dengan pesan cara memperbaiki. CLI `set-role`/`set-source` memvalidasi argumen dan memperbaiki berkas yang rusak.
- **Rantai lain yang dicoba dan tertutup:** `dropUser dbpanel_repl` di master (ditolak); `configure{role:replica}` di master (ditolak); `releaseRole` di master (ditolak, juga lewat `Pins.Release`); `configureReplication`/`dumpFrom`/`cloneFrom` ke sumber lain pada replika yang dipin (ditolak, sebelum `releaseRole`); `releaseRole` saat replikasi masih dikonfigurasi atau saat ada dump thread (ditolak); `Bootstrap` hint `master` pada server yang punya sumber replikasi (tidak dipin master, perbaikan `ce53d95`).

- **Laporan kesehatan:** batas 64 KiB, JSON tak terbaca diabaikan, `Seq` lebih kecil diabaikan (direset saat agent tersambung), `TakenAgoMS` negatif dijepit 0. Agent hanya memengaruhi server miliknya (id dari sertifikat mTLS). String agent hanya dirender lewat `html/template` (PoC 9 halaman: tidak ada payload mentah).
- **SSE:** `health_update` (`server_id`, `status`, `severity`) dan `alert_update` (`id`, `kind`, `server_id`, `open`) tanpa teks.
- **Fragmen dan JSON:** `GET /servers/{id}/status-fragment`, `/alerts/count`, `/jobs/{id}/log` di balik login (303 tanpa sesi), `no-store`, `CORP: same-origin`, `nosniff`; cookie `SameSite=Lax` tidak terkirim pada subresource lintas situs. `app.js` hanya memasukkan HTML fragmen milik panel (`innerHTML` dari respons same-origin yang ter-escape, dan ditolak bila `r.redirected`); log job ditulis dengan `textContent`.

- **Audit log:** semua handler POST yang mengubah keadaan menulis audit (26 jenis aksi, termasuk penolakan); IP dari `RemoteAddr` (bukan `X-Forwarded-For`); `detail_json` disaring dari kunci `password`/`token`/`secret` di semua kedalaman; username dari konteks sesi; tidak ada FK sehingga entri bertahan setelah server dihapus; `servers.id` `AUTOINCREMENT` sehingga id tidak dipakai ulang dan entri lama tidak salah atribusi.
- **Rahasia baru di log:** `createDumpUser` dan `createReplUser` mencatat user/host/require_ssl saja; registry agent menyamarkan field `password`; tidak ada token di `panel.log` (PoC).

### 8.4 Yang tidak bisa dijalankan atau dibuktikan

- Pengiriman ke Telegram sungguhan (lingkungan audit menolak `api.telegram.org` lewat proxy). Perilaku 429 dan antrean (SEC-46) dianalisis dari kode dan batas Telegram yang terdokumentasi.
- Eksploitasi SEC-42/43 lewat Hub dari panel yang benar-benar dibobol: perintah dikirim langsung ke `commands.Registry` agent nyata dengan parameter yang persis sama dengan yang dikirim Hub. Batas pin ada di agent, sehingga jalurnya identik.
- Rantai `releaseRole` → `dumpFrom`/`cloneFrom` dari donor penyerang tidak dijalankan sampai selesai. `configureReplication` ke host penyerang sudah membuktikan pin hilang, dan efek dump/CLONE sudah terbukti di audit Rencana 2.
- Perilaku `Pdeathsig` saat thread OS berakhir (SEC-51b) dan unit systemd (tanpa systemd di lingkungan audit).
- Uji di browser sungguhan untuk halaman baru. CSP dan escaping diverifikasi dari header, isi template, dan HTML yang dirender, bukan Chromium.
- Instance mysqld lama di `/var/tmp/dbpanel-test-*` yang sudah berjalan sebelum sesi audit ini (dibuat sesi lain sejak 2026-10-30) tidak disentuh.
