## 1. Ringkasan eksekutif

Tingkat risiko keseluruhan: **Tinggi**. Rencana 2 memberi agent kuasa admin MySQL penuh dan menambahkan 21 perintah `mysql.*`. Pekerjaan dasarnya rapi. Semua parameter divalidasi di agent sebelum menyentuh SQL atau argv. Identifier dikutip dengan backtick setelah lolos `dbNameRe`. Sandi yang tidak bisa memakai placeholder dikirim sebagai literal yang di-escape sesuai `sql_mode`; ini diuji pada 40 kombinasi sandi × 4 `sql_mode` dan hasilnya 40/40 benar tanpa injeksi. Tidak ada shell kecuali satu `sh -c` dengan argumen posisional. Unduhan memakai https saja dengan batas ukuran. Sandi tidak pernah masuk log, ParamsJSON, atau event. Semua route POST baru lolos pemeriksaan CSRF, dan semua header keamanan ada di setiap kelas respons.

Tiga temuan **Tinggi** harus selesai sebelum Rencana 2 dipakai di rumah sakit:

1. **SEC-26**: dump dari master dimuat dengan klien `mysql` tanpa `--binary-mode`. Baris `\! perintah` di aliran dump dijalankan **sebagai root** di server replika (PoC: `uid=0(root)`). Penyerang on-path antara replika dan master, server "master" palsu, atau panel yang dibobol bisa mendapat root di setiap replika.
2. **SEC-27**: akun `dbpanel_repl@'%'` memegang `RELOAD`, `SELECT ON *.*`, dan `BACKUP_ADMIN`, dan sandinya ada di setiap replika (tersimpan plaintext di `mysql.slave_master_info`). Siapa pun yang memegangnya bisa menghapus semua binlog dan riwayat GTID master (`RESET MASTER`, PoC berhasil), membekukan semua penulisan di master (`FLUSH TABLES WITH READ LOCK`, PoC berhasil), dan membaca semua database termasuk hash sandi semua akun MySQL.
3. **SEC-28**: rekomendasi blast radius dari SEC-22/§6.4 Rencana 1 tidak diterapkan, dan registry kini berisi perintah destruktif tanpa pagar lokal. Panel yang dibobol bisa menghapus database master produksi tanpa jejak binlog (`dropDatabases`, `dumpFrom DropExisting`), menimpa master (`cloneFrom`), membuat master menerapkan aliran binlog penyerang (`configureReplication`), dan **mengganti sandi akun MySQL mana pun, termasuk root dan akun aplikasi SIMRS** (`createReplUser` menjalankan `ALTER USER` pada akun yang sudah ada).

Tiga temuan **Sedang**:

- SEC-29: data pasien dan kredensial melintas LAN tanpa TLS terautentikasi. Replikasi memakai `SOURCE_SSL=0`. Sandi admin MySQL diketik di UI HTTP polos, sehingga dampak SEC-23 naik.
- SEC-30: unit systemd tidak diperbarui. `ProtectSystem=full` membuat agent jarak jauh tidak bisa menyimpan kredensial atau menulis config MySQL. mysqld yang dinyalakan lewat init script atau `mysqld_safe` ikut cgroup agent dan mati saat agent di-restart.
- SEC-31: tombol "Ulangi" pada job usang menjalankan langkah destruktif di server yang sudah dipakai job atau topologi lain.

Temuan final review C2, I3, dan I4 tumpang-tindih dengan SEC-31, SEC-29, dan SEC-26. Analisis keamanannya ada di sini, dan perbaikannya cukup sekali dalam satu gelombang.

## 3. Model ancaman

Model ancaman Rencana 1 (§3, butir 1–7) tetap berlaku. Rencana 2 menambah aset dan penyerang berikut:

- **Aset baru:** data pasien di master dan replika; akun admin MySQL tiap server (tersegel di agent, `/etc/dbpanel/mysql.cred`); sandi `dbpanel_repl` (tersegel di panel dan plaintext di setiap replika); ketersediaan master produksi (SIMRS berhenti kalau master read-only, terkunci, atau kehilangan binlog).
8. **Penyerang on-path di LAN DB** (ARP spoofing, port mirror, switch dibobol) antara replika dan master: menyadap aliran replikasi dan dump, atau menyamar sebagai master.
9. **Master yang dibobol atau server "master" palsu:** penyerang dengan root di master, atau host yang alamatnya diberikan ke agent sebagai sumber dump/CLONE.
10. **Pengguna MySQL biasa** di master atau replika (akun aplikasi SIMRS, akun laporan di replika, SQL injection di aplikasi): mencoba naik ke akun dbpanel atau ke OS.
11. **Panel yang dibobol** (butir 5 Rencana 1), kini dengan registry yang berisi perintah destruktif. Jalurnya realistis: UI HTTP polos (SEC-23), proses web root (SEC-06 belum diperbaiki).

### SEC-26 — Dump dimuat tanpa `--binary-mode`: perintah klien `\!` dari aliran dump berjalan sebagai root di replika
- **Tingkat:** Tinggi. CVSS-ish `AV:A/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H` ≈ 8.3: penyerang di jaringan mendapat root di host lain, di luar batas MySQL.
- **Dieksploitasi oleh:** (a) penyerang on-path antara replika dan master (dump tidak memverifikasi identitas server, SEC-29); (b) master yang dibobol atau server palsu di alamat sumber; (c) panel yang dibobol, yang bebas mengisi `Host`/`Port` di `mysql.dumpFrom`.
- **Lokasi:** `internal/agent/drivers/mysql/dump.go:214-216` (`loadArgs` hanya `--defaults-file` dan `--init-command`), `dump.go:421` (`h.Exec(ctx, pr, nil, loadBin, loadArgs...)`: keluaran `mysqldump` dari master dialirkan ke stdin `mysql`), `dump.go:157` (cek login lokal memakai argumen yang sama), `realhost.go:228-238` (proses anak agent, root). Proses agent dan panel (agent tertanam) berjalan sebagai root (`scripts/systemd/*.service`).
- **Serangan dan dampak:** klien `mysql` menafsirkan perintah klien di stdin, juga dalam mode batch: `\!`/`system` (shell), `\.`/`source` (membaca berkas), dan `\T`/`tee` (menulis berkas). Mulai 8.0.40 `--system-command` **aktif secara default**. `mysqldump` menyalin teks dari server apa adanya (`SHOW CREATE TABLE/PROCEDURE/TRIGGER/EVENT`). Server MySQL yang jujur menormalkan teks itu, sehingga pengguna biasa di master tidak bisa menyisipkan baris `\!` (dicoba, lihat bukti). Namun server palsu atau proxy MITM bisa mengembalikan `Create Table` berisi `;\n\! perintah\n`. Hasilnya adalah root di server replika: kunci mTLS agent (menyamar sebagai agent), `secrets.key` + `mysql.cred` (sandi admin MySQL replika), dan jalan masuk ke VLAN DB. Di rumah sakit, satu master yang dibobol menjadi root di semua replikanya, padahal replika sering dipakai sebagai cadangan atau DR.
- **Bukti:**
  ```
  # aliran yang dihasilkan mysqldump bila server mengembalikan Create Table yang disisipi:
  37:) ENGINE=InnoDB;
  38:\! id > .../PWNED_dump
  39:SELECT 1 DEFAULT CHARSET=utf8mb4 ...
  $ mysql --defaults-file=local.cnf "--init-command=SET sql_log_bin=0" < evil.sql     # = loadArgs agent
  ERROR 1064 (42000) at line 39: ...                (load gagal, tetapi terlambat)
  $ cat PWNED_dump
  uid=0(root) gid=0(root) groups=0(root)
  # perbaikan diuji:
  $ mysql --defaults-file=local.cnf --binary-mode ... < evil.sql   -> ERROR at line 38: Unknown command '\!'.   (berkas tidak dibuat)
  $ mysql --defaults-file=local.cnf --system-command=OFF ... < evil.sql -> 'system' command received, but the --system-command option is off. Skipping.
  $ mysql --defaults-file=local.cnf --binary-mode ... < real.sql  -> rc=0, tabel + procedure termuat (DELIMITER tetap jalan)
  # vektor dari master jujur (gagal): procedure dengan body "/*!99999 \! id > ... */" dibuat lewat driver Go,
  # SHOW CREATE PROCEDURE mengembalikan body tanpa komentar berversi itu.
  ```
- **Perbaikan minimal:** tambahkan `--binary-mode` ke `loadArgs` (berlaku untuk semua 8.0.x, 8.4, 9.x; menonaktifkan semua perintah klien kecuali `delimiter` dan `charset`). Tambahkan juga `--system-command=OFF` bila versi klien ≥ 8.0.40 (diketahui dari `mysql --version`), serta `--local-infile=0`. Tambahkan test dengan aliran berisi `\! touch <berkas>` yang wajib gagal tanpa membuat berkas. Pertahanan berlapis: SEC-29 (verifikasi identitas master) dan SEC-28 (agent hanya menerima sumber dump yang dipin).
- **Kapan:** sebelum rilis (satu argumen, sama dengan final review I4).

### SEC-27 — `dbpanel_repl@'%'` terlalu berkuasa: hapus binlog master, bekukan tulis, baca semua data; sandinya ada di setiap replika
- **Tingkat:** Tinggi. CVSS-ish `AV:A/AC:L/PR:L/UI:N/S:U/C:H/I:L/A:H` ≈ 8.3. Prasyaratnya hanya sandi satu akun yang tersebar ke semua replika dan tersimpan plaintext di sana.
- **Dieksploitasi oleh:** siapa pun yang memegang sandi replikasi: root atau agent di replika mana pun (juga replika yang hanya mengikuti satu database); akun MySQL di replika yang punya `SELECT` pada skema `mysql` (lazim untuk "user laporan" dengan `GRANT SELECT ON *.*`); penyerang on-path (`GET_SOURCE_PUBLIC_KEY=1`, SEC-29).
- **Lokasi:** `internal/agent/drivers/mysql/users.go:24` (`replGrants = "REPLICATION SLAVE, BACKUP_ADMIN, SELECT, RELOAD, LOCK TABLES, SHOW VIEW, TRIGGER, EVENT"` `ON *.*`), `users.go:54` (FromHost bawaan `%`), `internal/panel/orchestrator/prepare_master.go:104` (`FromHost: "%"`), `configure.go:123,215` (`bind_address=0.0.0.0`, SEC-40), `replication.go:285-290` (sandi masuk `CHANGE REPLICATION SOURCE`, yang oleh MySQL disimpan plaintext di `mysql.slave_master_info`), ruling T12 di ledger ("security audit must weigh restricting FromHost").
- **Serangan dan dampak:** satu akun dengan host `%` dipakai bersama oleh semua replika satu master.
  - `RELOAD` di MySQL 8.0 cukup untuk `RESET MASTER`, dan di 8.4+ untuk `RESET BINARY LOGS AND GTIDS`. Semua binlog dan riwayat GTID master hilang: semua replika berhenti (error 1236), dan rantai pemulihan point-in-time terputus.
  - `RELOAD` + `LOCK TABLES` memungkinkan `FLUSH TABLES WITH READ LOCK` yang ditahan selama sesi hidup. Semua penulisan SIMRS di master berhenti (pendaftaran pasien, resep, billing).
  - `SELECT ON *.*` membaca **semua** database, termasuk yang sengaja tidak dipilih untuk replika itu dan skema `mysql` (hash sandi semua akun, bisa dicoba di-crack offline). Filter replika (REPLICATE_WILD_DO_TABLE) tidak pernah menjadi batas kerahasiaan. Ruling T12 benar bahwa `BACKUP_ADMIN` dan `REPLICATION SLAVE` sudah membuka semua data, tetapi `RELOAD` menambah dampak integritas dan ketersediaan yang sebelumnya tidak ada.
  - Rantai realistis: pengguna laporan di replika membaca `SELECT User_name, User_password FROM mysql.slave_master_info`, lalu login ke master (yang kini mendengarkan di semua antarmuka) dan menjalankan `RESET MASTER` atau menahan FTWRL.
- **Bukti (mysqld 8.0.46 sementara, akun dibuat persis dengan `replGrants`):**
  ```
  --- baca semua database + hash sandi semua akun MySQL:
  Budi                         <- simrs.pasien
  app   $A$005$k*}             <- mysql.user.authentication_string
  --- sebelum: gtid_executed 0342…:1-4, binlog.000001 22567, binlog.000002 1272
  $ mysql -udbpanel_repl -p… -h127.0.0.1 -P33999 -e "RESET MASTER"     (berhasil)
  --- sesudah: gtid_executed [], binlog.000001 157
  $ (dbpanel_repl) FLUSH TABLES WITH READ LOCK; SELECT SLEEP(6)
  $ (root) INSERT INTO simrs.pasien …  -> ERROR 1205 Lock wait timeout exceeded (tulis terblokir 3,0 s = lock_wait_timeout)
  ```
- **Perbaikan minimal:**
  1. Pisahkan akun. `dbpanel_repl` hanya `REPLICATION SLAVE` (ditambah `BACKUP_ADMIN` sementara bila CLONE dipilih, lalu dicabut). Akun dump `dbpanel_dump` dibuat per job oleh langkah "Siapkan replika" dengan sandi acak baru dan hak `SELECT, SHOW VIEW, TRIGGER, EVENT, LOCK TABLES, RELOAD`, lalu `DROP USER` atau `ACCOUNT LOCK` saat job selesai (juga saat gagal atau dibatalkan).
  2. Host akun = alamat replika (satu akun per replika, `dbpanel_repl_<id>@'<ip-replika>'`), bukan `%`. Alamat replika diketahui saat `create_replica`.
  3. `REQUIRE SSL` pada akun replikasi (lihat SEC-29).
  4. README: jangan beri akun di replika `SELECT ON *.*`, karena `mysql.slave_master_info` menyimpan sandi replikasi. Pakai grant per database.
- **Kapan:** sebelum rilis (butir 1–2); butir 3 bersama SEC-29.

### SEC-28 — Agent tanpa pagar lokal untuk perintah destruktif; `createReplUser` mengambil alih akun MySQL mana pun
- **Tingkat:** Tinggi. CVSS-ish `AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H` ≈ 9.1. Prasyaratnya panel dibobol, tetapi dampaknya mencakup semua server DB, termasuk master produksi.
- **Dieksploitasi oleh:** pemegang kendali panel (proses web root yang menghadap LAN, SEC-06 masih terbuka; cookie lewat HTTP polos, SEC-23) atau pencuri kunci CA panel.
- **Lokasi:** `internal/agent/commands/registry.go:64-91` (dispatch tanpa log atau kebijakan), `internal/agent/session.go:96` (setiap request di goroutine sendiri, tanpa batas), dan pemeriksaan per perintah:
  - `databases.go:68-118`, `mysql.dropDatabases`: hanya menolak bila replika sedang berjalan atau ada thread binlog dump yang tersambung saat itu; `DROP DATABASE` dijalankan dengan `sql_log_bin=0`.
  - `dump.go:60-149`, `mysql.dumpFrom`: hanya `refuseRunningReplica`; tidak ada cek thread binlog dump; `DropExisting` → `DROP DATABASE`, lalu mode GTID `ON` → `RESET BINARY LOGS AND GTIDS` di server itu.
  - `clone.go:43-...`, `mysql.cloneFrom`: hanya `refuseRunningReplica`; `clone_valid_donor_list` diatur agent sendiri ke host dari panel.
  - `replication.go:369-404`, `mysql.configureReplication`/`startReplica`: tanpa cek apakah server ini sumber bagi server lain atau berisi data produksi.
  - `users.go:81-118`, `mysql.createReplUser`: `ALTER USER <akun> IDENTIFIED BY …` bila akun sudah ada; `userNameRe` menerima `root`, `accountHostRe` menerima `localhost`.
  - `configure.go`: `mysql.configure` dengan `role=replica` menulis `read_only/super_read_only` ke config; `mysql.setReadOnly`; `mysql.restart` tanpa syarat.
  - `replication.go:512`, `mysql.resetReplica`.
  - `connect.go:89-123`, `mysql.connect`: mengganti akun tersimpan; host bebas.
  - `snapshot.go:120`/`replication.go:224`: cek database sistem peka huruf besar-kecil, berbeda dengan `databases.go:51`.
- **Serangan dan dampak** (setiap baris adalah satu pesan JSON ke agent master produksi; tidak satu pun ditolak agent):

  | Perintah dari panel jahat | Efek di master produksi |
  |---|---|
  | `mysql.dropDatabases{Databases:["simrs"]}` saat replika sedang putus atau belum dibuat | database SIMRS hilang, tanpa catatan di binlog (`sql_log_bin=0`), sehingga PITR dari binlog juga tidak bisa |
  | `mysql.dumpFrom{Host:<penyerang>, Databases:["simrs"], DropExisting:true, …}` | DROP, **`RESET BINARY LOGS AND GTIDS`** (semua replika putus), isi diganti data penyerang; plus root lewat SEC-26 |
  | `mysql.cloneFrom{Host:<penyerang>}` | seluruh instance ditimpa donor penyerang |
  | `mysql.configureReplication{Host:<penyerang>}` + `mysql.startReplica` | master menerapkan event binlog penyerang (UPDATE/DELETE data pasien) dengan hak penuh applier |
  | `mysql.createReplUser{User:"root", FromHost:"localhost", Password:X}` | `ALTER USER 'root'@'localhost' IDENTIFIED BY X` → root diambil alih (auth_socket diganti sandi). `User:"simrs_app", FromHost:"%"` → aplikasi SIMRS tidak bisa login (layanan berhenti), penyerang masuk sebagai aplikasi lewat `bind_address=0.0.0.0` |
  | `mysql.setReadOnly{On:true}` atau `mysql.configure{Role:"replica"}` + `mysql.restart` berulang | master hanya-baca atau terus restart (DoS) |
  | ratusan `mysql.connect`/`preflight` paralel | setiap panggilan membuka sampai 4 koneksi, `max_connections` master habis, SIMRS ditolak |
  | `mysql.dumpFrom{Databases:["SYS"], DropExisting:true}` di server `lower_case_table_names=1` | skema `sys` terhapus (cek sistem di `validateSnapshot` peka huruf besar-kecil) |

  Spesifikasi menyebut bahwa master tidak pernah direstart tanpa klik manusia, dan bahwa server tujuan yang berisi database lain ditolak. Keduanya hanya ditegakkan di **panel**, bukan di agent. Satu-satunya batas di agent adalah validasi bentuk parameter, dan itu sudah benar. Tidak ada kebijakan lokal, token konfirmasi, batas konkurensi untuk perintah sinkron, atau log lokal untuk setiap perintah. `dropDatabases` dan `resetReplica` mencatat log hanya bila berhasil; `configureReplication` dan `preflight` gagal tanpa jejak di journald agent.
- **Bukti:** penelusuran kode di atas. `createReplUser`: `users.go:95-107`, yaitu `SELECT COUNT(*) FROM mysql.user WHERE user=? AND host=?` lalu, bila > 0, `ALTER USER ` + akun. Statement `ALTER USER ... IDENTIFIED BY` dengan literal hasil `quotePassword` terbukti dieksekusi apa adanya (PoC escaping, bagian 5).
- **Perbaikan minimal** (ini rekomendasi §6.4 Rencana 1, dipersempit ke yang murah):
  1. **Peran lokal yang dipin agent:** `/etc/dbpanel/role` (atau `agent-policy.yaml`, milik root, tidak bisa ditulis lewat perintah panel) berisi `master`, `replica`, atau `unassigned`. Berkas ini ditulis oleh agent sendiri saat `configure` pertama untuk peran itu dan hanya bisa diubah operator di host. Agent menolak `dropDatabases`, `dumpFrom`, `cloneFrom`, `configureReplication`, `resetReplica`, dan `setReadOnly{On:true}`/`configure{Role:replica}` bila perannya `master`. Selain itu, penolakan juga berlaku bila server berisi database non-sistem yang tidak tercatat sebagai "dikelola dbpanel" (daftar disimpan agent saat dump/clone).
  2. **`createReplUser`:** nama user tetap di sisi agent (`dbpanel_repl`/`dbpanel_dump`); tolak `ALTER USER` bila akun yang ada tidak bertanda `ATTRIBUTE '{"managed_by":"dbpanel"}'` (8.0.21+) atau tanpa komentar dbpanel; tolak host `%`.
  3. **Sumber yang dipin:** `dumpFrom`/`cloneFrom`/`configureReplication` hanya menerima `Host:Port` yang sama dengan sumber yang tercatat di agent setelah konfigurasi replika pertama. Perubahan sumber membutuhkan konfirmasi lokal (perintah CLI di host).
  4. `dumpFrom` dan `cloneFrom` menolak bila `BinlogDumpThreads > 0` atau `log_replica_updates`/peran master; cek database sistem tidak peka huruf besar-kecil di semua validator.
  5. Semafor untuk perintah sinkron (mis. 4) dan satu perintah destruktif per server pada satu waktu.
  6. `Dispatch` mencatat setiap perintah (nama, parameter tanpa field `password`, hasil/error, durasi) di level Info ke journald.
- **Kapan:** butir 2, 4, 5, dan 6 sebelum rilis (murah); butir 1 dan 3 sebelum Rencana 3 (promote/failover akan menambah perintah yang lebih berbahaya).

### SEC-29 — Data pasien dan kredensial melintas LAN tanpa TLS terautentikasi
- **Tingkat:** Sedang. CVSS-ish `AV:A/AC:H/PR:N/UI:N/S:U/C:H/I:L/A:N` ≈ 5.9. Naik ke Tinggi bila VLAN DB tidak terisolasi: data rekam medis terus-menerus, dan sandi replikasi membuka SEC-27.
- **Dieksploitasi oleh:** penyerang di segmen LAN antara replika dan master (pasif untuk replikasi, aktif untuk yang lain), atau antara browser operator dan panel.
- **Lokasi:**
  - `internal/panel/orchestrator/create_replica.go:476-480` (`SSL: false` selalu; komentar: tidak ada CA untuk verifikasi);
  - `internal/agent/drivers/mysql/replication.go:289` (`GET_SOURCE_PUBLIC_KEY = 1`);
  - `dump.go:258-298` (berkas opsi tanpa `ssl-mode`/`ssl-ca` plus `get-server-public-key`);
  - `clone.go:82-83` (`CLONE INSTANCE` tanpa `REQUIRE SSL`, sehingga bisa jatuh ke plaintext);
  - `conn.go:21-46` (DSN TCP tanpa TLS; go-sql-driver v1.9.3 meminta kunci publik RSA server tanpa verifikasi pada caching_sha2 lewat plaintext, `auth.go:408-442` di modul);
  - `internal/panel/web/handlers_mysql.go:87-120` (sandi admin MySQL dikirim lewat form di UI HTTP polos, SEC-23).
- **Serangan dan dampak:**
  - (a) `SOURCE_SSL=0` mematikan enkripsi yang sebenarnya sudah tersedia: MySQL 8 membuat sertifikat sendiri (`auto_generate_certs`). Seluruh aliran binlog (setiap INSERT/UPDATE data pasien pada database yang diikuti) melintas jaringan dalam plaintext.
  - (b) Dengan `GET_SOURCE_PUBLIC_KEY=1` di koneksi tanpa TLS, penyerang aktif yang menyamar sebagai master mengirim kunci RSA miliknya dan menerima sandi `dbpanel_repl` (lalu SEC-27).
  - (c) `mysqldump` (ssl-mode PREFERRED) dan CLONE memang mengenkripsi, tetapi tidak memverifikasi identitas master. MITM bisa menyamar, yang membuka SEC-26.
  - (d) Rencana 2 membuat UI HTTP polos (SEC-23, diterima di Rencana 1) membawa **sandi admin MySQL** (sering `root`) di body POST. Dampak penerimaan risiko SEC-23 naik dan perlu ditinjau ulang oleh pemilik produk.
  - Konteks regulasi: UU PDP No. 27/2022 dan Permenkes 24/2022 (rekam medis elektronik) menuntut perlindungan kerahasiaan data kesehatan, termasuk saat transit.
- **Bukti:** pernyataan kode di atas. `SOURCE_SSL = ` + `"0"` dari `p.SSL=false` dikonfirmasi oleh `sourceStatement` (`replication.go:280-291`). Final review I3 menyetujui `SOURCE_SSL=1` bila master melaporkan TLS tersedia (enkripsi saja).
- **Perbaikan minimal:**
  1. (Gelombang ini) `SOURCE_SSL=1` setiap kali master mendukung TLS, dan `GET_SOURCE_PUBLIC_KEY=0` bila TLS dipakai; `ssl-mode=REQUIRED` di berkas opsi dump (hapus `get-server-public-key`); `CLONE ... REQUIRE SSL`; akun replikasi `REQUIRE SSL`.
  2. (Rencana 3) CA panel menerbitkan sertifikat server MySQL untuk master (dipasang `mysql.configure`), lalu replika memakai `SOURCE_SSL_CA` + `SOURCE_SSL_VERIFY_SERVER_CERT=1`, dump memakai `ssl-mode=VERIFY_CA ssl-ca=…`, dan CLONE memakai `clone_ssl_ca`.
  3. Form "Hubungkan MySQL": tulis peringatan bahwa sandi dikirim lewat HTTP polos, sarankan membuka panel lewat VLAN manajemen atau tunnel SSH sampai HTTPS hadir, dan prioritaskan HTTPS panel (Rencana 6) lebih awal.
- **Kapan:** butir 1 sebelum rilis; butir 2 sebelum Rencana 3; butir 3 sebelum rilis.

### SEC-30 — Unit systemd tidak diperbarui untuk Rencana 2
- **Tingkat:** Sedang (kelemahan konfigurasi dengan dampak ketersediaan). CVSS-ish `A:H` pada master non-systemd; integritas hardening terancam karena operator akan mencabutnya.
- **Lokasi:** `scripts/systemd/dbpanel-agent.service` dan `web/templates/agent-install.sh.tmpl:85-121` (`ProtectSystem=full`, komentar "Plan 2 must open what it manages … before writing there"), `scripts/systemd/dbpanel-panel.service` / `scripts/install.sh:164-190` (`ProtectSystem=strict`, `ReadWritePaths=/var/lib/dbpanel /etc/dbpanel`), `internal/agent/cli.go:127-131` (`secrets.LoadOrCreate("/etc/dbpanel/secrets.key")`), `internal/agent/drivers/mysql/service.go:64-79,116-126` (init script dan `sh -c 'nohup mysqld_safe … &'` dijalankan sebagai anak agent).
- **Serangan dan dampak:**
  - (a) `ProtectSystem=full` membuat `/etc` hanya-baca untuk agent. Akibatnya `secrets.key` tidak bisa dibuat (log "cannot open the credential sealing key"), `Creds` bernilai nil, dan `mysql.connect` menjawab "agent tidak punya tempat menyimpan kredensial MySQL". `mysql.configure` tidak bisa menulis `/etc/mysql/conf.d/zz-dbpanel.cnf` atau `/etc/my.cnf`, dan `mysql.install` gagal karena `/usr` hanya-baca. Agent tertanam di panel mengalami hal yang sama untuk `/etc/mysql`. Test E2E tidak berjalan di bawah systemd, jadi ini tidak terdeteksi. Risikonya, operator lapangan akan "memperbaiki" dengan membuang semua hardening.
  - (b) Untuk tata letak init script (aaPanel) dan `mysqld_safe`, mysqld dijalankan dari dalam unit agent, sehingga ia mewarisi cgroup dan namespace agent: `PrivateTmp`, `ProtectHome`, `ProtectSystem`, `NoNewPrivileges`.
    - Socket `/tmp/mysql.sock` (bawaan aaPanel) hanya terlihat di `/tmp` privat agent, sehingga aplikasi di host kehilangan socket.
    - Saat `dbpanel-agent` di-restart (`Restart=always` setelah crash, upgrade, `systemctl restart`), `KillMode=control-group` ikut menghentikan mysqld master, sehingga SIMRS berhenti.
- **Bukti:** isi unit dan alur kode di atas. Tidak dijalankan karena lingkungan audit tanpa systemd.
- **Perbaikan minimal:**
  - Unit agent: `ReadWritePaths=/etc/dbpanel /etc/mysql /etc/my.cnf.d` serta direktori config yang ditemukan (atau `ProtectSystem=` dilonggarkan hanya untuk langkah yang perlu).
  - Jalankan `mysql.install`, start lewat init script, dan `mysqld_safe` melalui `systemd-run --unit=dbpanel-<aksi> --wait --collect` (unit transien di luar sandbox dan cgroup agent), bukan sebagai anak proses agent.
  - Samakan untuk agent tertanam di panel.
  - Tambahkan cek isi unit ke `install_test.sh` dan langkah verifikasi manual di checklist rilis (`systemd-analyze verify`, connect dan configure di host systemd nyata).
- **Kapan:** sebelum rilis.

### SEC-31 — "Ulangi" pada job usang menjalankan langkah destruktif di server yang kini milik job/topologi lain
- **Tingkat:** Sedang. CVSS-ish `AV:N/AC:L/PR:H/UI:R/S:U/C:N/I:H/A:H` ≈ 6.1: salah klik pada tombol yang masih tampil, dengan dampak penghapusan data.
- **Lokasi:** `internal/panel/orchestrator/runner.go:391-405` (`Retry` hanya menolak bila ada job aktif lain di server itu), `runner.go:353-365` (`ReopenJob` lalu `run(from=CurrentStep)`), `runner.go:637-644` (`setReplicaState(Creating)` untuk baris replika server itu, milik siapa pun), `create_replica.go:376-427` (`resetReplica`, `dropDatabases(WipeList)`, CLONE/dump dari master job lama), `web/handlers_jobs.go:183` (`CanRetry` untuk setiap job `failed`). Sama dengan final review C2 dan minor ledger T12 "old failed job retryable after its row was replaced".
- **Telusur:**
  1. Job A `create_replica` (master M1, target T) gagal di tahap 4 setelah pengguna menyetujui `WipeList=[simrs]`.
  2. Pengguna membuat job B untuk T. `StartCreateReplica` membuang baris `failed`, lalu B selesai: T menjadi replika `ready` (bisa dari master M2).
  3. Hari berikutnya pengguna membuka `/jobs/<A>` dari riwayat dan mengklik "Ulangi dari tahap ini".
  4. `Retry` → `ActiveJobForServer(T)` kosong → `run(4)` → baris replika B diubah menjadi `creating` → `dropDatabases([simrs])` di T (data replika B hilang) → dump/CLONE dari **M1** → `configureReplication` ke **M1**, padahal baris T di DB masih menyebut topologi M2.
  Bila T sudah dijadikan master setelah baris replikanya dibuang (final review: "clone over a repurposed master"), CLONE menimpa master. `Approve` punya celah yang sama untuk job `waiting` yang ditinggal.
- **Perbaikan minimal (sesuai ruling C2):** di bawah `startMu`, `Retry`/`Approve` menolak job yang sudah digantikan: ada job yang lebih baru untuk server itu; baris replika tidak ada, milik topologi lain, atau tidak `failed`/`creating`; peran server berubah; atau daftar database job perubahan sudah berbeda. UI menyembunyikan tombolnya dan menjelaskan alasannya. Tambahkan test regresi untuk skenario di atas.
- **Kapan:** sebelum rilis.

### SEC-32 — Root mengeksekusi klien MySQL dan `kill` berdasarkan path/pid file yang bisa dikendalikan pengguna `mysql`
- **Tingkat:** Rendah. CVSS-ish `AV:L/AC:H/PR:L/UI:N/S:C/C:H/I:H/A:H` ≈ 7.0 secara teori, Rendah karena hanya pada instalasi tarball atau aaPanel yang direktorinya dimiliki `mysql`.

### SEC-37 — Pembatalan `mysql.install` mengirim SIGKILL ke apt/dpkg

### SEC-39 — FTWRL singkat di master saat dump dimulai; replika bisa ditulis selama load (diterima)
- **Ruling:** ledger T9 (FTWRL inheren pada `--single-transaction --set-gtid-purged=ON/COMMENTED`; `read_only` dicabut selama load).
- **Risiko residual:** kueri panjang di master (laporan bulanan) membuat FTWRL menunggu, dan selama itu semua penulisan SIMRS ikut tertahan. Selama load yang bisa berjam-jam, replika dapat ditulis oleh klien lain, misalnya aplikasi laporan yang salah konfigurasi, sehingga data replika menyimpang diam-diam. Bila agent mati (SIGKILL) di tengah load, `read_only` tetap OFF sampai MySQL restart. Final review I8 menambahkan pemberitahuan di kedua form.
- **Mitigasi:** pemberitahuan "lakukan di jam sepi"; `--lock-wait-timeout` di argumen `mysqldump` agar FTWRL gagal cepat daripada membekukan master; selama load, `max_connections` sementara atau `offline_mode=ON` di replika agar hanya akun admin yang bisa masuk.

### SEC-40 — `bind_address=0.0.0.0` di master yang tadinya loopback (diterima)
- **Ruling:** ledger T8(2); teks restart di `prepare_master.go:197` menyarankan firewall.

### SEC-41 — TLS replikasi hanya enkripsi tanpa verifikasi CA (diterima setelah perbaikan I3)
- **Ruling:** final review I3 (`SOURCE_SSL=1` bila master mendukung TLS, tanpa verifikasi CA di v1).
- **Risiko residual:** penyerang on-path aktif tetap bisa menyamar sebagai master. Penyadapan pasif tertutup. Lihat SEC-29 butir 2 untuk Rencana 3.

## 5. Yang diperiksa dan dinilai aman

- **Escaping literal sandi** (`users.go:122-130`, `connect.go:360-362`, `replication.go:293-302`, `clone.go:81-83`, `install.go:480,555-562`): sql_mode dibaca dari **sesi yang sama** (`db.Conn`) dengan sesi yang menjalankan statement. Diuji dengan salinan persis `quotePassword` terhadap mysqld 8.0.46. Sepuluh sandi diuji (`a'b`, `a\'b`, `abc\`, `\\'`, `x' OR '1'='1`, `p\'; DROP USER app@localhost; -- `, `%_"` + backtick, `ä漢字🙂`, `\n\t\0` sebagai teks, `''''\\\\`) di empat `sql_mode` (default, `NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES,NO_BACKSLASH_ESCAPES`, `ANSI`). Hasilnya **40/40** `CREATE USER` dan `CHANGE REPLICATION SOURCE` sukses, login dengan sandi asli sukses, dan akun `app` tetap ada (tanpa injeksi). Karakter kontrol ditolak sebelum SQL (`unicode.IsControl`, termasuk NUL). Sandi panjang ditolak > 32 rune untuk `SOURCE_PASSWORD`. Binlog berisi hash (`IDENTIFIED WITH 'caching_sha2_password' AS '$A$005$…'`), bukan sandi.
- **Identifier:** `dbNameRe` `^[\p{L}\p{N}_$][\p{L}\p{N}_$-]{0,63}$` tidak menerima backtick, kutip, backslash, spasi, titik, garis miring, `%`, atau newline; tidak boleh diawali `-` (aman sebagai argv `--databases`). Semua `DROP DATABASE` dan `CREATE` memakai backtick setelah validasi (`dump.go:373`). Pola LIKE meng-escape `_` (`replication.go:257-263`). `userNameRe` `^[A-Za-z0-9_$]{1,32}$`, `sourceHostRe`/`accountHostRe` tanpa kutip atau backslash, IPv6 wajib `net.ParseIP`, GTID set lewat regex ketat dan batas 64 KiB. `server_id`, port, dan timeout berupa integer. Nilai `SET PERSIST` konstan (`configure.go:128-135`).
- **argv dan berkas opsi:** tidak ada shell, kecuali `sh -c 'nohup "$0" --defaults-file="$1" …'` dengan argumen posisional (`service.go:126`), yang aman dari injeksi. `--defaults-file` selalu argumen pertama, sehingga `~/.my.cnf` tidak bisa mengganti akun. Berkas opsi 0600 (`CreateTemp` O_EXCL + `Chmod`) di `/tmp` privat unit, nilai dikutip ganda dengan `\` dan `"` di-escape, kontrol ditolak, dan dihapus dengan `defer`. Sandi tidak pernah ada di argv. `--init-command=SET sql_log_bin=0` di klien load dan berhak dicek sebelum data diubah (`checkClients`).
- **Unduhan `mysql.install`** (`install.go:633-681`): skema `https` wajib di URL awal dan di setiap redirect (maks. 10), timeout 10 menit, batas 64 MiB (`LimitReader` +1 untuk mendeteksi kelebihan), berkas sementara 0600 O_EXCL dihapus setelah dipakai. URL mirror hanya dari variabel lingkungan agent (milik root host, tidak bisa diatur panel) dan wajib `https` + ekstensi yang benar. Userinfo disamarkan dengan `u.Redacted()` di log dan error. Tidak ada `--nogpgcheck`/`--allow-unauthenticated`. Paket server diverifikasi apt/dnf dengan kunci MySQL yang dipasang paket rilis; paket rilis sendiri dipercaya karena datang lewat HTTPS (dicatat; pin SHA-256 untuk paket rilis disarankan sebagai penguatan). Install menolak server yang sudah punya `mysqld`.
- **Rahasia di log/ParamsJSON/event:** setiap jalur sandi ditelusuri.
  - Sandi repl: dibuat `crypto/rand` (24 karakter, 62 simbol, ≈143 bit), disegel AES-256-GCM (`panel.key` 0600 O_EXCL, berkas tidak biasa atau izin longgar ditolak), dibuka hanya saat dikirim lewat Hub ke agent.
  - Sandi admin: form → `Hub.Call` → agent `Creds.Save` (JSON tersegel 0600, rename atomik). Panel tidak menyimpannya dan tidak menampilkannya ulang di form (`connectForm` tanpa sandi).
  - `jobState`/ParamsJSON tidak punya field sandi. `logf` dan semua `Logger.Info` agent hanya mencatat user, host, dan port.
  - Pesan error `json.Unmarshal` tidak memuat nilai.
- **Job runner agent:** satu job pada satu waktu (`ErrBusy`), id 128 bit acak, panic ditangkap, ring log 2000 baris. CLONE dibatalkan dengan `KILL QUERY <connection_id>` pada sesi CLONE sendiri (bukan memutus koneksi), dan restart setelah fase data memakai `context.WithoutCancel` dengan batas waktu sendiri. `restore()` read-only memakai `WithoutCancel` + 30 s.
- **Orkestrator:** `Approve` dan `Retry` diikat ke `CurrentStep` saat diklik (klik ganda yang terlambat tidak menyetujui tahap berikutnya); `cancelJob` mengabaikan job yang sudah selesai; `refuseBusy` dan `startMu` mencegah dua job pada satu server. Konfirmasi hapus database terikat ke SHA-256 daftar yang ditampilkan (`hashList`); bila daftar berubah, job kembali menunggu. Flag form `ConfirmWipe` tidak pernah menggantikan persetujuan di job. Target replika divalidasi di server (`slices.ContainsFunc(p.Targets…)`, crafted `target=1` → 400). Master tidak bisa menjadi target (`MasterServerID == TargetServerID` dan pemeriksaan `self_peer` lewat `server_uuid`). `HandleEvent` hanya menerima event dari server yang sedang ditunggu. Satu-satunya celah logika yang ditemukan adalah SEC-31.
- **Web:** semua route baru di belakang `RequireLogin`; semua POST (9 route baru) lewat `sameOrigin` + `limitForm`. Origin asing, `null`, atau tanpa header → **403** (diuji). Tanpa cookie → 303 ke `/login`. `GET` ke route POST → 405. Host asing → 421. ID path diparse `ParseInt`/regex `^[0-9a-f]{32}$` untuk job (`/servers/-1`, `/replicas/9999…9` → 404). Tidak ada mass-assignment: handler membaca field tertentu dan membangun `CreateReplicaParams` sendiri. Tidak ada redirect yang memakai input pengguna (`?pesan=` hanya kunci map). Error internal → `msgInternal`.
- **XSS:** `html/template` di semua halaman baru. Payload `<img onerror>`, `<script>`, `<svg onload>`, `"'`, `${7*7}`, `{{7*7}}` di `jobs.error`, `job_steps.message`, `job_log.message`, dan nama database (ParamsJSON) semuanya ter-escape di binary yang berjalan. `data-*` berisi integer, status dari daftar tetap, dan JSON lencana ter-escape (`data-badges="{&#34;attention&#34;…`). `data-connected` sengaja dipakai alih-alih `data-online` (konteks JS html/template). `app.js` menulis log dan pesan dengan `textContent`, tanpa `innerHTML`, `eval`, atau `new Function`. Template tanpa `<script>` inline, atribut `on*`, `style=`, atau `javascript:`. Ekspresi Alpine hanya nama properti atau method (build CSP 3.14.9).
- **Store:** migrasi 0003 dalam transaksi; semua kueri berparameter (sufiks `ORDER BY … LIMIT ?` konstan); `UpdateJob` menolak job yang sudah final.
- **Bootstrap (§6.1 Rencana 1):** perintah pairing memuat sha256 skrip; skrip memuat sha256 binary per arsitektur dan sidik jari CA; `agent pair` menolak CA lain (`ErrCAMismatch`) dan redirect (`CheckRedirect`); `curl --max-redirs 0`; token lewat `-K -` dan `DBPANEL_TOKEN`, bukan argv; nilai skrip lewat `shq`.
- **Proses dan log:** slog meng-quote nilai (injeksi log tidak mungkin); `lineWriter` memotong baris apt di 4096 byte.

### 8.4 Yang tidak bisa dijalankan atau dibuktikan

- Server MySQL palsu atau proxy MITM yang mengubah jawaban `SHOW CREATE TABLE` secara langsung. Diganti dengan aliran dump hasil rekayasa yang dialirkan ke argumen klien yang sama dengan agent. Bahwa `mysqldump` menyalin teks `Create …` dari server apa adanya dianalisis dari perilaku alat.
- Perilaku unit systemd (SEC-30), `systemd-analyze security`, `KillMode` saat agent di-restart: lingkungan audit tanpa systemd.
- Eksploitasi SEC-28 terhadap agent jarak jauh lewat Hub (perlu panel jahat). Dibuktikan dari kode perintah per perintah; efek SQL yang menjadi dasar (`ALTER USER`, `DROP DATABASE`, `RESET MASTER`) sudah dijalankan langsung.
- Apakah `SHOW PROCESSLIST`/`performance_schema` menampilkan sandi `CLONE INSTANCE … IDENTIFIED BY` selama CLONE berjalan (perlu dua instance dan donor aktif); binlog terbukti menulis ulang `CREATE USER`.
- Langkah RHEL `mysql.install` (`secureRoot`, `auth_socket`) dan unduhan dari repo.mysql.com (tidak terjangkau dari sesi audit).
- Uji di browser sungguhan untuk halaman baru. CSP diverifikasi dari header dan isi template, bukan Chromium.
