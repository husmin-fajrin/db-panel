### E-1: completeness proof forged through names. ADDRESSED (one residual race, Important, is under Residual Risks)

**What the code does now**

- connect.go:410 sets `grantPrivileges = ([A-Z0-9_ ,]+)`.
- connect.go:416 sets ``globalGrant = ^GRANT <privs> ON \*\.\* TO (.+?)( WITH GRANT OPTION)?$``.
  - The privilege list cannot hold a backtick, a quote, a parenthesis or a newline.
  - `(?s)` is gone, so the account group `.+?` cannot cross a newline either.
- rebuild_load.go:306 sets ``revokeRow = ^REVOKE <privs> ON .+ FROM (\S+)$``.
- `listingProof(grants, user, host)` (rebuild_load.go:315-345) works like this:
  - A GRANT row counts only when `m[2]` is exactly ``` `user`@`host` ``` or `"user"@"host"`.
  - Any row that starts with `REVOKE ` and either does not parse or names another account returns `(false, false)`.
  - Privileges are no longer upper-cased after the match. The class already demands upper case.
- `proofAccount` (rebuild_load.go:251-258):

  - The user must match `^[A-Za-z0-9_.$-]+$` and the host `^[A-Za-z0-9_.%:/-]+$`. In Go, `$` means end of text, so a trailing `\n` is refused.
- `listingComplete` (rebuild_load.go:269) builds `SHOW GRANTS FOR '<user>'@'<host>'` from the checked parts with `quoteString`.

### E-4: error-log open through a swapped directory. ADDRESSED for the briefed risk (device open)

The risk that was ADDRESSED is that a device gets opened. The fixer's wording about symlinked directories is inaccurate; details follow.

**Code** (startlock_guard.go:384-433):

- `syscall.Open(path, O_PATH|O_NOFOLLOW|O_CLOEXEC)`, then `fstat`, which must show a regular file.
- Then `openLogFile("/proc/self/fd/N")` with `O_RDONLY|O_NONBLOCK|O_CLOEXEC`, a second `fstat`, which must show a regular file, and `os.SameFile`.

**Checks**

- `oPath = 0x200000` is right for amd64 and arm64 (and the generic Linux value). The agent is Linux-only. The constant would be wrong on alpha, parisc and sparc, which are not release arches.
- O_PATH never calls a driver's `open`, so the watchdog-arming race of C-5 is closed.
- With O_NOFOLLOW, a symlink as the last component gives a descriptor of the link itself. `fstat` then shows `S_IFLNK`, which is refused.
- The reopen goes through the magic link of the already-resolved inode, so a swap of any path component after the O_PATH open changes nothing. A FIFO or device can never reach the reopen, because the first `fstat` already required `S_IFREG` on the same inode.
- No descriptor leaks:
  - `fd` becomes `pf` immediately, with `defer pf.Close()`.
  - `f` has `defer f.Close()`.
  - The only path without a wrapper is `syscall.Open` failing, which yields no fd.
  - `os.NewFile` on an O_PATH fd does not register it with the poller (no O_NONBLOCK flag).
- If `/proc` is missing, the reopen fails and the error takes the existing "unreadable" path (a warn).

**What a hostile mysql uid can still make root open and read**

It controls `log_error` through its option files (`printDefaults`, startlock.go:743) and the directory around it, so it can name any path at all, directly or through symlinked directories. For example, `log_error=/etc/shadow`, or `d -> /etc` plus `d/shadow`.

Root's O_PATH open follows the intermediate symlinks. `fstat` shows a regular file, and root reads its last 64 KiB (`bootLogTail`).

This was possible before the round as well, and needed no race: `Lstat` followed the intermediate directories, and the old open did too.

**What reaches anyone**

The tail goes only to `scanBootstrapFailure` (startlock_guard.go:443-462). That function returns just one timestamp, taken from a line holding exactly `Failed to open the bootstrap file <start-lock path>`, which `EventQuarantineStartFailed` then carries. No content of the file reaches the panel, the operator or the log. The warn line logs the attacker's path string and an errno.

The confidentiality impact is therefore nil, as before. The only content-dependent effect is a forged "start failed" event, which the mysql uid could produce anyway by writing its own log.

**Side effects that remain**

These are pre-existing and Low:

- Regular files on special filesystems still get read. `/proc/kmsg` is `S_IFREG`, and reading it consumes kernel messages destructively (log loss for a klog reader). O_NONBLOCK keeps it from blocking.
- A file on a FUSE mount owned by the mysql uid can block the read forever when `user_allow_other` is enabled, and the guard holds `promoteMu` while it waits. With `promoteMu` stuck, later ticks are skipped (TryLock), so the guard's quarantine branch stops running.

**The fixer's claims**

- "a symlinked intermediate directory is refused": not as a rule. `TestReadTailDirectorySwappedForSymlink` is refused only because the targets are a FIFO and `/dev/null`, which are not regular files. A symlinked directory that leads to a regular file is followed and read.
- That test would also pass at the old code (Lstat followed the directory and saw a FIFO), so it is not a RED test. The discriminating test is `TestReadTailSwapBetweenCheckAndRead`, where the old code opened the FIFO through the seam.
- "harmless" for a swap between the two opens: true. The checked inode itself is read.

### E-6: listing-refusal texts (bare GRANT replaced). PARTIALLY ADDRESSED

**Attacker-influenced content**

- The only variable is `quoteAccount(account)`, and it is printed only for an account that passed `proofAccount`. The user is limited to `[A-Za-z0-9_.$-]` and the host to `[A-Za-z0-9_.%:/-]`, so pasting the GRANT into the mysql client cannot break out of `'…'` or add a statement.
- One edge remains: `$` is allowed in the user. If an operator pastes the advice into a double-quoted shell argument (`mysql -e "…"`), a user such as `a$HOME` expands, and the GRANT names another account. That account is either nonexistent, which makes the GRANT fail (ERROR 1410) and with the advised sequence leaves super_read_only OFF (see (iii) below), or one the attacker made. The fixer's README draft uses `<<'EOF'`, a quoted heredoc that does not expand, which is safe. The README must keep that form, and it should say that the account is written into the heredoc and not into `-e "…"`. This is Low.
- The unsupported-name text carries no variable.

**Is every statement true against the code?**

- "akun MySQL %s yang dipakai agent tidak punya hak SHOW DATABASES": true in the normal cases. It is loose when the cause was a query error or a privilege held only through a role, but the advice still works there, as the C re-review already noted.
- "Server ini baca-saja":
  - It is emitted only when `mark != nil` (a rebuild of a quarantined server, dump.go:125) or at the settle, both on a quarantined server.
  - In `listBefore` the refusal happens while read-only is lifted, but the deferred `restore()` puts it back before the operator can act on it.
  - So the statement is true in every context it is emitted in.
- "Ulangi dari tahap ini" works for both steps, because each step opens a new pool (`openAdmin` → `OpenDB`). This is proven by `TestRebuildPartialRevokeAccount` (copy step) and `TestRebuildRoleOnlyAccountAtSettle` (configure step).
- **Not true at abb56bc:** README, bagian "Memberi hak SHOW DATABASES di server yang dikarantina" does not exist (`git grep abb56bc -- README.md`). README.md:1843-1848 still quotes the old text and says "Jalankan `GRANT` itu". The fixer was told to make no README change, and its report lists what the README needs. Until that README change lands, the agent points the operator at a section that does not exist.
- On the job page, `redact.Quotes` censors the account, the README section name and the button name (`Censored = "'…'"`; double quotes are censored too). See N-1.

**Safety of the advised sequence on a quarantined old master**

- Normal run (ii): `read_only` stays ON throughout. `super_read_only` is OFF only for the GRANT. `sql_log_bin=OFF` keeps gtid_executed unchanged, so no errant GTID is created, and the persisted values are untouched. This is correct.
- During the OFF window, other sessions with SUPER or CONNECTION_ADMIN can write. That window lasts milliseconds.
- Interrupted run (iii): a failed GRANT stops the client, and `super_read_only` stays OFF until someone sets it by hand or MySQL restarts. I confirmed the fixer's statement that the guard does not repair this: `guardQuarantined` (quarantine.go:302-304) returns early on `d.guard.up && sameRun` and reads the flags again only after a MySQL restart or a load. While the flag is OFF, any account with SUPER or CONNECTION_ADMIN can write to the quarantined old master, and that includes the agent's own account and a panel-chosen admin account.
- This is acceptable only with the README warning the fixer drafted. A procedural fix is better (see N-3).

**Do the tests exercise it on a super_read_only target?**

Yes. `grantAsAdvised` (rebuild_listing_test.go) asserts `read_only` and `super_read_only` are ON before, runs the real `mysql -S <socket> -uroot` client with the exact sequence, and asserts ON/ON and an unchanged gtid_executed after. Both real-mysqld tests then retry on the same driver. Path (iii) is not tested.

**Verdict**

The code text is correct and safe. The item stays PARTIALLY ADDRESSED for two reasons, both in N-1:

- The advice depends on a README section that does not exist at the head (pending the controller's README change).
- On the job page, the advice loses the section name and the button name.

## Residual Risks

- **R-1 (Important, pre-existing; mechanism measured in this round).** The proof reads the ACL cache, while the listing runs under the connection's login-time global privileges.
  - A session that holds SUPER and can grant SHOW DATABASES (or SELECT) on `*.*` can toggle GRANT/REVOKE for the agent's account. The settle's connection (opened by `OpenDB`'s ping) may then authenticate during a revoked phase while `SHOW GRANTS` runs during a granted phase. The proof passes, the listing hides the old databases, and the quarantine ends.
  - Each lost try keeps the approval and can be retried.
  - The `listBefore` side of the same race is harmless: a database the dump loads must be visible to the account anyway.
  - Possible closures:
    - Cross-check the listing against the datadir's schema directories, which root can read. A directory MySQL did not list then means "not proved".
    - Re-authenticate (COM_CHANGE_USER) after the proof and list on that session. This does not stop toggling alone.
    - Require `super_read_only` ON at both ends of the proof and listing, and read it on every guard tick, so that toggling requires a visible flag change.
  - I cannot verify MySQL's internal privilege caching beyond the fixer's measurement.
- **R-2 (Low).** `SHOW GRANTS` output under `sql_quote_show_create=OFF` was not measured. If MySQL honours that setting there, every row prints unquoted, and the proof fails for every account. That is fail-closed, an availability problem only. Setting `sql_quote_show_create=1` and `sql_mode` without ANSI_QUOTES on the proof's session would remove the dependency.
- **R-3 (Low).** Through `log_error`, the mysql uid can still make root read the tail of any regular file. Only a timestamp of a fixed-phrase line comes back. A destructive `/proc/kmsg` read is possible, and so is a hang on a FUSE file when `user_allow_other` is on, with the guard stuck under `promoteMu`.
- **R-4 (carried from C).** These remain open:
  - RENAME TABLE into a named database during the load window.
  - The system schemas are not compared.
  - The F-10 order (a weak account stored before the quarantine).
  - A second local MySQL instance counts as local.
  - Mandatory and other role privileges are not counted (fail-closed; documented in the plan).
- **R-5 (Low).** A `$` in an account can expand if the advice is pasted into a double-quoted shell argument. The README must keep the quoted heredoc.

## Out-of-Scope Observations
