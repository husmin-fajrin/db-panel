## Findings

### WB-1 — The master page still tells the operator to promote by hand, and says the panel cannot — Tinggi
- Attacker: none needed; "an operator in a hurry".
- Where: web/templates/_status.html:50-63 (`down-guide`), shown by `status-full` (:46) on the master page
  (master_detail.html:26) and through GET /servers/{id}/status-fragment; set at
  internal/panel/web/views_monitor.go:104 (`DownGuide = role master && status "Diduga tumbang"`).
- What it says, at the moment the master is presumed down: "Yang bisa dilakukan sekarang … 4. Bila master tidak
  bisa dipulihkan, jadikan replika itu master secara manual. Di MySQL replika itu jalankan: `STOP REPLICA; RESET
  REPLICA ALL; SET PERSIST super_read_only=OFF; SET PERSIST read_only=OFF;` … 5. Arahkan aplikasi ke alamat IP
  replika itu. Catatan: panel belum bisa melakukan langkah ini; versi berikutnya akan melakukannya otomatis."
- Why it is wrong now: emergency promote exists (the same page has the card "Ganti master … mode darurat",
  master_detail.html:95-111, and guide "Promote darurat"). The box is a left-over of the plan before promote; no
  ledger or audit mentions it (grep: only one design-ledger line about its `role`).
- Steps: master goes down → operator opens the master page → follows step 4 literally on a replica.
- Result: a replica made writable outside the panel, with `RESET REPLICA ALL`; the old master is never
  quarantined (no promotion record, no start lock, role still `master` in the panel and on its agent). When it
  comes back it is writable: two masters taking writes — the outcome the strict mode exists to prevent. The
  panel's topology is also wrong from then on (it still names the old master).
- Confirmed: reading only (template, the flag, and that nothing else replaces the box).
- Rating note: the scale lists "a misleading screen or guide" under Sedang; I rate it Tinggi because the text is the
  panel's own instruction to turn read-only off, shown exactly during an outage, it states the panel cannot do the
  job, and following it once leads to two masters without any further mistake.
- Smallest fix: replace the box by one sentence and a link ("Master tidak terjangkau: buka Promote… (mode darurat);
  langkahnya di Panduan, 'Promote darurat'"), and drop the SQL. No spec decision changes; it is new operator text
  (owner's text list).

### WB-2 — Twenty wrong logins from four addresses block every password confirmation and every login — Sedang
- Attacker: anyone who can reach the UI port from four source addresses, without an account; in the model: a
  compromised database server (it can add addresses on its interface), or someone on the LAN.
- Where: handlers_auth.go:63 (`UserLimiter.Blocked`), :93 (`UserLimiter.Fail` for every wrong password, from any
  address), handlers_confirm.go:163 (`UserLimiter.Allow` before the confirmation's password check), panel.go:53-55
  (5 per address, 20 per username, 15 minutes).
- Steps (run): logged in as admin from 127.0.0.1; `POST /confirm` with the right password → 200. Then 5 wrong
  logins for `admin` from each of 127.0.0.11–.14 (all answered 200 "salah"). Then the same logged-in session,
  right password: `POST /confirm` → **429** `{"error":"Terlalu banyak percobaan konfirmasi; coba lagi dalam 1
  menit."}`; a login with the right password from a fresh address → **429**.
- Impact: while the attacker repeats 20 requests per 15 minutes, nobody can confirm with the password: no promote
  (also not the emergency one), no Buka kunci master, no rebuild, no Resync, no delete, no certificate change; and
  nobody can log in. The message says "1 menit"; the block lasts up to 15 minutes. The README's remedy
  (`systemctl restart dbpanel-panel`, "Login pertama") ends every session and the attacker locks the account again
  in seconds. There is no other way to run an emergency promote. With WB-1 on the screen, the likely fallback is
  the manual promote.
- Confirmed: by running (above).
- Smallest fix: let wrong passwords at `/login` count per address only for the purpose of blocking `/confirm`; keep
  `/confirm`'s own budget (ConfirmLimiter, per username) and let only failures at `/confirm` feed the login
  budget, not the reverse; correct the message. Needs a decision: the 5b spec's "shared budget" (comment at
  handlers_confirm.go:137-140) was chosen on purpose.
- Variant, read only: `Limiter.Allow` refuses a new address while 10,000 addresses are tracked
  (ratelimit.go:49-63), so an attacker with that many addresses (IPv6) blocks logins from new addresses. Rendah.

### WB-3 — `sameOrigin` accepts an `http://` origin of the panel's own host and port — Sedang
- Attacker: someone on the network path (or who controls DNS) plus a logged-in admin's browser.
- Where: handlers_auth.go:165-177 (`u.Host != r.Host` only; the scheme is not compared); the UI port also serves
  plain HTTP (tlsui.go:895-913: `/sertifikat`, the download, `/static/`; everything else 301).
- Steps: the attacker answers any plain `http://<panel>:8080/...` request of the admin's browser (he can cause one
  from any page) with his own page; that page is origin `http://<panel>:8080` and posts a form to
  `https://<panel>:8080/<route>`. The browser sends `Origin: http://<panel>:8080`.
- Run: `POST https://127.0.0.1:28580/servers/1/snooze` with a session cookie and `Origin: http://127.0.0.1:28580`
  → 303, action done and audited (compare `Origin: https://evil.example` → 403, `Origin: null` → 403).
- Not run (unconfirmed part): that the browser attaches the `__Host-` `SameSite=Lax` cookie to that POST. Browsers
  that treat http and https of one host as the same site (Firefox and Safari by default, as far as I know) do;
  Chromium's schemeful same-site does not. A browser test with Firefox would confirm it.
- Impact: every state-changing route that needs no password token (see the route table: settings incl. Telegram
  bot and chat, thresholds, backup folder, master source address, marks, snooze, stop replica, prepare master,
  approve of a restart, cancel job, "Sudah saya alihkan", new pairing token). HSTS does not help when the panel is
  opened by IP address (the README's own example), since HSTS never applies to an IP.
- Smallest fix: in `sameOrigin` also require `u.Scheme == "https"` (the UI is HTTPS only; the tests that post over
  httptest would set an https origin). No spec decision.
- Test that would prove it: `TestCSRFOnNewRoutes` with `origin = "http://" + req.Host`, want 403.

### WB-4 — A logged-in session without the password can replace a paired server's agent; the pairing is not audited — Sedang
- Attacker: a stolen or unattended session (no password).
- Where: router.go:202 `POST /servers/{id}/token` → handlers_servers.go:890-911 (no `requireConfirm`; a paired
  server gets a re-pairing token); the command with the token is on GET /servers/{id}
  (handlers_servers.go:843-852); agentapi/pair.go:124-177 consumes it, issues the certificate, cuts the old agent
  (:163-166) and writes **no audit row** (only `auditPairRefused`, :200, for the refused local token; success is one
  journald line, :170).
- Steps: POST the token route for the master's server → read the command on the page → run `dbpanel agent pair`
  from any host that reaches the panel.
- Gain: the real agent is disconnected and its certificate refused; the attacker's process is "the agent" of that
  server: it receives every command and secret the panel sends there (MySQL account typed in Hubungkan MySQL,
  replication account, MySQL certificate keys), answers health reports and gate rows as it likes, and can refuse
  or fake promote and quarantine. The neighbour of the same kind, Hapus server (which only cuts the agent), needs
  the password and the typed name.
- What the operator sees afterwards: one audit row "Perintah pemasangan dibuat"; nothing says that, from where, or
  with which hostname an agent paired.
- Confirmed: reading only.
- Smallest fix: require a confirmation token (new action, bound to the server) for a token of a **paired** server,
  and audit `agent_pair` on success too (address, hostname bounded). Needs a decision (spec 5.7 lists the
  confirmed actions).

### WB-9 — Headers that could be stricter without breaking the panel — Rendah
Measured value in brackets.
- HSTS [`max-age=31536000`]: no `includeSubDomains`. Adding it does not break the panel. Caveat: HSTS is per host
  name for every port, so it already switches any other plain-HTTP service on the same name to HTTPS in that
  browser (the README mentions aaPanel on such hosts); `includeSubDomains` widens that to sub-names. A decision.
- CSP [`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self';
  object-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; worker-src 'none'; manifest-src
  'self'`]: no `unsafe-inline`, no `unsafe-eval`, no wildcard — sound. Could be `default-src 'none'` with
  `font-src 'self'`, `media-src 'none'`, `frame-src 'none'`; no `require-trusted-types-for 'script'` (two
  `innerHTML` sinks for same-origin fragments, app.js:752, :822); no `report-to`, so a violation in a browser is
  seen by nobody.
- Permissions-Policy [camera, microphone, geolocation, payment, usb, serial, hid, bluetooth, display-capture,
  clipboard-read off]: accelerometer, gyroscope, magnetometer, midi, fullscreen, picture-in-picture,
  publickey-credentials-get, screen-wake-lock, xr-spatial-tracking, autoplay, encrypted-media, idle-detection,
  local-fonts, window-management, browsing-topics are not listed. Little to gain: nothing foreign can load.
- SSE [`Cache-Control: no-cache`] (sse.go:77): the stream carries job log lines; `no-store` fits better.
- Logout: no `Clear-Site-Data`. Pages are `no-store` already.
- Cookie [`__Host-dbpanel_session=<64 hex>; Path=/; HttpOnly; Secure; SameSite=Lax`, no Max-Age]: sound. `Lax`
  is deliberate (links from Telegram); see C6 for what a cross-site GET can do.
- TLS: UI listener `MinVersion: TLS 1.2`, Go's default suites (tlsui.go:416-418); agent listener TLS 1.3 with a
  required client certificate (ca/ca.go:333-335). TLS 1.3 only for the UI is possible for every current browser.
Confirmed: by running (values) and reading.

### WB-15 — Integrity of what root runs — Info (documented, unchanged)
- `install.sh` is piped from `main` to `sudo bash`; the binaries are checked against `SHA256SUMS` of the same
  release (install.sh:68-100); no signature. README "Keamanan rilis" says so and advises a tag.
- The agent install: the pairing command pins the panel's key and the script's hash; the script holds the hash of
  the binary the panel serves (agentapi/install.go, binhash.go). So integrity on the wire is checked, but the
  anchor is the panel: a compromised panel serves its own agent binary to every server where an operator runs
  "Pasang ulang agent" as root. That moves the trust boundary of the model (the agent is the boundary; the panel
  may be compromised) for any server re-installed during a compromise. Worth one sentence in the README.
- Build tools: Alpine (CSP build) 3.14.9 is fetched with an integrity value (vendor.sh); the Tailwind CLI v4.1.14
  and daisyUI v5.1.29 are downloaded and run without one (tailwind.sh:19-38); their output app.css is committed.

### WB-16 — Guide and flash texts — Rendah
- Guide "Melepas kunci master lama dengan tangan", step 2: `… WHERE STATUS="ENABLED";` uses double quotes for a
  string; with `sql_mode` ANSI_QUOTES the check fails with an error an operator in a hurry may take for "no
  events". Use `'ENABLED'` (the statement is inside `mysql -e '…'`, so write it with `-e "…"` and single quotes).
- Guide "Replika yang tersambung di luar alur panel", step 4: `sudo dbpanel agent set-role quarantined` "tidak
  bertanya". The only guard against running it on the new master is the `hostname` comparison of step 3. If run
  on the wrong server it makes that server read-only (an outage, no data loss; `set-role master` reverts). The
  guide states it was never run end to end; I did not run it either.
- Placeholders (`<kode>`, `<host:port>`, `<berkas kunci>`) pasted unchanged make bash fail with a syntax or
  "no such file" error before anything runs — safe.
- Guide "Memperbaiki baris merah / Akun panel": the account gets `GRANT ALL PRIVILEGES ON *.* … WITH GRANT
  OPTION` — the same power as root; the row's purpose is telling the agent's sessions from root's, not least
  privilege. The password is generated with `openssl rand`, typed only inside the mysql client (which keeps
  `IDENTIFIED` statements out of its history by default); the replica rule ("jangan pernah mematikan baca-saja di
  replika") is stated before the steps. Sound as written.
- Flash after "Lepas replika … hentikan" (handlers_mysql.go:207-209) gives the SQL that opens the detached
  server for writes. The server is no longer in a topology; acceptable, noted.

### WB-17 — Small disclosures and limits — Info
- The login page and `/sertifikat` show the panel version without login (layout.html:74); the downloadable CA
  certificate lists the panel's names, addresses and the subnets of the host's interfaces (name constraints).
- No `WriteTimeout` on the UI server (servers.go:125-133, for SSE) and no connection cap: a client that reads

- "Prasyarat tidak bisa dibaca: %s" and `shownError` show the panel's own error text (a store error's words) to a

### WB-18 — Audit chain: what the panel notices — Info (inherent, partly documented)
The chain is an unkeyed SHA-256 over the row's fields (store/audit_chain.go:17-31). The panel's page says "Rantai
utuh sampai #N" (handlers_audit.go:44-66). It notices a row changed or removed in the middle. It does not notice
rows cut from the end, nor a whole chain rewritten by whoever can write panel.db (the `dbpanel` user: drop the
two triggers, rewrite, recompute, recreate). The second copy in journald is the only anchor, and whether the
journal leaves the host is a hand-set mark (K6). After a compromise of the panel process an operator sees an
intact chain; only a comparison with an off-host journal shows the truth.

### A. Route table

passes `SecurityHeaders` and, in the panel, `RequireHost` (servers.go:228). "Token" = the password confirmation
token of `POST /confirm`. "Gate" = the precondition gate judged in the handler before the token.

Without login:

| Method, path | Handler | CSRF check | Token | Rate limit | Audit |

### B. OWASP Top 10 (2021)

**A01 Broken Access Control — finding (WB-4, WB-5, WB-13); the rest sound.**
Every UI route except static, login, logout and the certificate page sits behind `authed`/`authedPost`
(router.go:192-265; run: `GET /` logged out → 303, `POST /servers/1/backup` logged out → 303). Method confusion:
the mux patterns carry the method; run: `GET /servers/1/delete` → 405 `Allow: POST`, `PUT /login`, `TRACE /`,
`OPTIONS /login` → 405. Forced browsing: unknown paths → 404 text, static directories → 404 (noDirFS,
router.go:365-378; run). Object references: ids are parsed as int64 (`pathID`) or matched (`jobIDPattern`,
`ValidSalvageName` `^[0-9]{8}T[0-9]{6}Z-[0-9]+\.sql$`); a token is consumed for (user, action, kind, id) in one
UPDATE (store/confirmations.go:36-52), so a token of one server, job or file does not work on another; a
replica route needs a replica row, a master route a topology, the connections fragment a topology member
(handlers_oldmaster.go:192-236). There is one role (admin), so there is no user-to-user boundary to cross.
Unauthenticated disclosure: WB-17.

**A02 Cryptographic Failures — sound; notes in WB-9.**
UI: TLS ≥ 1.2, Go default suites, certificate per handshake (tlsui.go:416-418). Agent channel: TLS 1.3, client
certificate required and verified (ca/ca.go:320-335), ECDSA P-256. Files (measured in the scratch run): config
and data directories 0700; `ca.key`, `mysql-ca.key`, `web-ca.key`, `web.key`, `panel.key` (32 bytes),
`admin-initial-password`, `local-pair-token`, `panel.db` 0600; `ca.crt` 0644. Writes are atomic with 0600
(tlsui.go:589-612). `panel.key` seals with AES-256-GCM and a random nonce (internal/secrets/box.go). Passwords:
bcrypt cost 12, input capped at 72 bytes before hashing (auth/password.go; handlers_auth.go:55). Tokens:
session 32 bytes of crypto/rand in hex, only in memory; confirmation 32 bytes, base64url, stored as SHA-256
(handlers_confirm.go:183-188); pairing 75 bits, stored as SHA-256 (store/tokens.go). Secrets in logs, audit rows
and pages: the password and the token are never audited (`scrubDetail` drops keys named password/token/secret,
audit.go:279-282); a typed unknown username is stored as a short hash only and not sent to the journal
(audit.go:284-293, :110-117); the Telegram token field is always empty. In URLs: the pairing token
(`/agent/install?token=`, sent by curl over pinned HTTPS, not logged by the panel) and the salvage token (query).

## Residual risks (inherent or accepted; worst outcome each)
- A session without the password (R2, spec 5.7 and WB-4/5/6/13): alerts redirected or silenced, a gate row made
  green, an agent replaced. Worst: an operator acts on a false green screen, or commands and secrets for one
  server go to an attacker's process.
- Plain HTTP on the UI port for the certificate page: someone on the path can change the page, the fingerprint
  and the certificate (the page says so). Worst: a browser trusts an attacker's CA for the panel's names and
  subnets and the admin's password is read.
- `SameSite=Lax` kept on purpose: clicked cross-site links reach the GETs of C6.
- Audit chain without a key and with a hand-set forwarding mark (K6, WB-18). Worst: a compromised panel rewrites
  its audit log and the page still says intact.
- Unsigned releases and `install.sh` from `main` (documented). Worst: a forged release runs as root everywhere.
- The panel supplies agent binaries (WB-15). Worst: servers re-installed during a panel compromise run the
  attacker's agent as root.
- One admin role, no password change in the UI, lock-out counters in memory.
