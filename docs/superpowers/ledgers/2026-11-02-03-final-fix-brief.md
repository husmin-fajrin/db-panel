## Audit items

Source: docs/superpowers/security/2026-11-02-audit-plan-3.md (read SEC-42, 43, 44, 46, 47, 48, 51(a) and §7 in full).

- **J (SEC-42, Tinggi — must fix).** On a pinned master: `mysql.createDumpUser` only accepts names matching `^dbpanel_dump_[0-9a-f]{8}$`, a literal IP host (`net.ParseIP`, never `%`/`_`), and refuses when the account already exists (never ALTER); `mysql.createReplUser` refuses when the account already exists (no ALTER on a pinned master; password rotation is CLI/Plan 4 — keep the create path for a fresh `dbpanel_repl`); `mysql.restart` is refused on a pinned master unless the last `mysql.configure` in this agent process reported `NeedsRestart` (one restart per such configure); `mysql.configure{role:master, server_id:N}` on a pinned master ignores a ServerID different from the current one (SEC-51a). Implement in `refusedByRole`/handlers (pins.go), with regression tests: createDumpUser{dbpanel_repl}, createDumpUser{…@'%'}, createDumpUser for an existing account, createReplUser for an existing account, restart without a pending configure — all refused on a pinned master; the orchestrator's normal flows (prepare_master's createReplUser on an unpinned server then restart after NeedsRestart; create_replica's per-job dump account from the replica IP) must still pass (run the orchestrator tests and the E2E).
- **K (SEC-44, Sedang).** `audit.go`: cap `detail_json` at 2 KiB total (each string ≤128 runes, each list ≤64 items, truncated with a marker); for REJECTED input never store the raw values — store field names and lengths only (e.g. `{"confirm_name_len": 7, "wipe_list_count": 3}`); `login_failed` stores the username only when that account exists, otherwise "(tidak dikenal)" plus a short SHA-256 prefix. Tests: a 64 KiB rejected wipe_list yields a detail ≤ 2 KiB without the raw names; unknown-username login_failed row has no raw username.
- **L (SEC-47).** Settings page: show the same plain-HTTP warning as the MySQL connect form above the token field when the page is served over plain HTTP; the `settings_update` audit detail records the new values of `telegram_chat_id` and `panel_base_url` (never the token). Tests.
- **M (SEC-46, "bila murah").** Minimal flap control in the notifier: for a given (server, kind), if an alert is reopened less than 5 minutes after the previous one of the same kind closed, do not send a new open message immediately; instead send one message at most every 5 minutes saying "⚠️ <server>: <kind awam> berkedip N kali dalam 5 menit terakhir" (and the normal "pulih" only when it has stayed closed ≥ 1 minute). Keep it simple and tested (fake clock: 100 open/close cycles in 2 minutes → ≤ 2 messages).
- **N (docs, SEC-43/45/48/52).** README corrections: the panel CAN release a replica's role/source pins through "Lepas dan hentikan" / "Hapus server" / a cancelled creation (what that means and that only the master pin is immutable from the panel); the audit log is tamper-resistant against the application only, not against root on the panel host; Bootstrap of a pin needs the panel's role hint (a master is pinned on "Siapkan master", a replica on "Buat replika"); a production master should not live on the panel host (the embedded agent's pins are not a boundary against the panel process). Also list what data leaves to Telegram (server names, statuses, errno, internal IPs/links) for the owner's data-protection assessment.
- **Deferred to Plan 4 (do NOT implement; the controller ledgers them):** SEC-42 item 4 (dump without a RELOAD network account), SEC-43 item 1 (releaseRole keeps the source pin), SEC-45 hash chain, SEC-46 ingest rate limit/retention, SEC-48 pin status in HealthSnapshot + "Master tidak dipin" alert, SEC-49 UX, SEC-50 redaction of quoted data at ingest, SEC-34 readLimit, SEC-23 HTTPS.
