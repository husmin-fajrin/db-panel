Rulings:
- R1: `dbpanel agent lock-master` writes the lock with Candidate "cli"; the guard treats "cli" as "no candidate": it never unlocks or quarantines by itself; only `unlock-master` (or a later lockForPromote replacing it? no — refused while a lock exists) clears it — cost if wrong: a CLI-locked master stays locked until an operator unlocks it, which is the operator's intent.
- R2: `mysql.promote` runs as an agent job (jobs.Runner, like dumpFrom) so its 10-minute relay-log wait reports progress through the existing job.* events; the orchestrator drives it with the existing agent-job step helper (agentjob.go) — cost if wrong: one extra plumbing layer; the alternative (a 10-minute blocking RPC) would hit hub call timeouts.
- R3: SEC-62 — PromoteView marks any server whose agent_version differs from the panel version as "Agent perlu dimutakhirkan" and ineligible (candidate or master for planned promote); StartPromote refuses with the same message; unknown_command from any promote command fails the step with the clear message from 4a's tlsCall mapping — cost if wrong: an operator must update agents before promote, which the README already requires.
- R4: SEC-63c and SEC-63g are deferred to Plan 4c (hardening), recorded there — cost if wrong: none for promote.
